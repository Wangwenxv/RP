# 微信玩家图片批次数量限制移除交接

更新：2026-11-24。适用于原单卡微信的玩家上传与识图链路。

同日后续：用户确认保留按需参考工具，另外解除微信工具次数、主请求轮数和两张参考限制；历史图工具新增 `messageIds`。本页图片批次改动保留，最新工具行为、费用和真实测试见 [视觉工具交接](./wechat-visual-tools-handoff.md)。

## 原因

“只能发送四张”来自工程自身的视觉输入预算，并非微信或图片 API 的统一限制。连发模式可以保存第五张图片，但 `assets/js/app/27-wechat-media.js` 的 `buildWechatVisualMessages` 在本轮尚未回复的新图超过四张时抛出“本轮最多识别 4 张新图，请分批发送”，因此请求不会到达聊天模型，待回复图片也无法正常处理。

同文件还有两处配套限制：`getWechatFollowupImages` 拒绝超过四张的旧图批次，数量与序号指代只覆盖较小范围；`rememberWechatImageDescriptions` 只处理返回描述数组的前四项。只删除报错会导致第五张之后的照片仍缺少后续描述与追问依据。

## 当前行为

- 本轮尚未回复的玩家新图全部按发送顺序附入视觉请求，工程不再设置固定图片张数上限，不截取前四张。
- 独立画面核对与工具续写沿用完整附件；每张核对图片仍须返回一条有效资料，漏图、重复或未知编号继续拒绝。查看已附的第五张及后续图片不重复读像素或调用识图。
- 识图返回的 `image_descriptions` 全部按本轮允许的消息 ID 写回。无效条目与未知 ID 被忽略；未查看的旧图与已有说明不能被覆盖。
- 明确追问“这五张”“那12张”“这十二张”“第五张”等时，读取最近的完整连续图片批次，保留原顺序和编号。阿拉伯数字支持多位数，中文数量支持十、百、千。
- 旧图批次仍必须能在前48条记录内找到最近一张；找到后继续读取完整连续组，48条不再截断组内图片。仍不跨 RP 段、不同发送者、不同批次或30分钟剧情间隔。数量不符、批次混有描述卡或部分组员超出时间范围时，不拿部分照片凑数。
- 普通下一轮继续只携带历史短描述，图片原件和缩略图仍存储在原资源库。

## 使用与生效

本项目没有构建步骤，刷新页面加载修改即可，无需迁移数据库或重新导入角色卡。

1. 在微信输入框开启“连发”。
2. 用现有附件入口逐张选择图片，每张点“发送”；可以连续发送五张及以上。
3. 点“让对方回复”，本轮全部待回复照片一起进入模型请求。

附件入口仍逐张选择，此次没有新增多文件选择界面。普通模式仍每次发送后立即请求回复。

## 保留的边界

本次去掉的是玩家图片批次的固定张数上限。单文件12 MiB、缩放长边1600、首次解码像素上限24 Mi等资源校验继续生效；缩略图最多四张并发读取只是排队控制，不限制消息数量。角色与分支隔离、停止请求、过期结果丢弃、存储失败和资源缺失处理继续沿用。

模型与服务商可能另外限制请求体积、图片数和上下文长度。大量照片会增加请求体积、识图耗时和费用；工程不主动分批或新增付费重试，服务商拒绝时沿用失败提示，并保留待回复消息。底层网络重试沿用原机制。

角色一次被动决策最多生成一张图片、RP 主动微信每轮一次联系等是独立规则，保持原行为。同日后续已解除两张角色参考与查看工具次数限制。多角色世界端玩家上传没有在本次新增。
