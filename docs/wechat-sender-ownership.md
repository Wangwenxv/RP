# 微信发送者归属与玩家草稿交接

日期：2026-11-08。沿用原 UI，不改变角色卡、微信输入框或聊天记录格式。

## 问题边界

用户本次确认的问题是：**玩家想说/想发送的台词，被模型变成当前角色主动发出的微信。** 这与单纯在旁白里声称“已发送”、或工具代写玩家回复，属于不同的错误。

微信工具此前已经写入 RP 的 system，同时作为原生 `tools` schema 发送；不是完全缺少工具说明。现有说明强调一条消息、发送条件、调用次数和玩家回应点，但多处仍使用泛称“角色”，没有在工具说明中用本轮真实姓名明确发送方向，也没有具体区分玩家草稿与角色的新消息。

角色卡作为 `[Character]` 资料放在 user 角色的背景消息中；其中还会出现“他给她发某句话，她回复”的惯例/示例。实际玩家输入、卡片引语和 NPC 台词虽然同在上下文中，归属仍须保持。仅禁止“新增以玩家为发送者的消息”不够：把玩家的原话改成角色发出，也会造成反向通信。

本次没有该轮完整 API 请求，不能断言单个预设或卡片条目是唯一原因；以上是实际请求组装和工具说明中可以确认的归属缺口。

## 现在的区分

以玩家陈璃、角色苏祈雪为例：

| 玩家输入 | 应保留的事实与方向 | 当前角色工具的用途 |
| --- | --- | --- |
| 我想给苏祈雪发：到宿舍了吗 | 陈璃的草稿/意向，尚未发送；苏祈雪没有因此收到 | 不据此调用，不搬成苏祈雪的台词 |
| 我给苏祈雪发：到宿舍了吗 | 陈璃 → 苏祈雪的明确发送叙述；是否读到仍须依据 | 若角色确有回应，发送她自己的回答；不反向发送原句 |
| 让苏祈雪给我发：到宿舍了吗 | 明确指定苏祈雪 → 陈璃的消息 | 工具可用且能通信时按此方向执行 |
| 帮我发给她 | 玩家要求代发自己的消息 | 当前角色的单向工具不能执行玩家代发 |

未明确标注其他说话人的真实玩家第一人称“我”属于玩家；有来源的角色引语仍属于原角色。叙事人称、镜头切换和卡片实例不改变发送者。

角色仍可依据自己的处境、已收到的信息和独立动机主动联系玩家。玩家的草稿本身不构成她的联系动机，也不会自动让她知道玩家在别处想说什么。其他 NPC 的消息不能借当前角色的工具发送。

## 实现

1. **最后组装的 system 增加发送归属。** `buildWechatSenderBoundary` 纳入本体 `player_agency`，使用每轮真实玩家/角色姓名、当前实际提供的微信工具名。普通 RP、工具续写、基础/增强记忆及提要都经过这一入口；微信回复协议同样注入归属规则。没有 RP 发送工具时明确能力缺失，被动微信仍使用自身回复 JSON 协议。
2. **schema 与调用提醒明确执行对象。** `14-tools-runtime.js` 在 function 描述、`content` 参数、system 工具说明及最新输入提醒中写入「本体角色 → 玩家」。旧存档无需重存工具描述，实际 schema 每轮重新构造。玩家明确指定角色说的台词仍可发送，不用“内容与玩家文字相同”作为拒绝标准。
3. **角色资料标注来源。** `[Character]` 背景加具名说明：设定、第一人称与台词示例属于角色卡资料，不是玩家的新输入或发送记录。最终玩家提醒再次说明玩家草稿不可变成角色来信。
4. **回执明确实际身份。** `deliverActiveWechatMessage` 返回由程序填写的 `sender:{role:'assistant',characterId,name}` 与 `recipient:{role:'user',name}`。它们是工具结果，不是允许模型填写的参数；参数仍拒绝任意 `sender/role`。`queued:true/delivered:false/awaitingPlayer:true` 的含义不变，排队不代表送达、已读或回答。
5. **压缩和检索保持方向。** 三类总结的来源规则增加发送者/收件人及草稿/已发送区别，原文检索结果也提醒玩家草稿不能证明角色已发出或收到。旧 AI 虚拟聊天、卡片惯例和摘要不能反向充当发送成功证明。

`buildWechatSenderBoundary` 位于请求末尾加入的本体约束中，避免被前面的用户正则、可选 COT 或旧卡片设置移除。工具续写保留原生签名和 tool-call 配对；没有增加纠错模型、网络请求或“必须联系玩家”的触发逻辑。

## 生效与局限

刷新页面即可对已导入角色生效，无需重导角色卡，也不需修改存档。磁盘卡片本次保持原内容；历史正文、错误微信、已有记忆和提要不会自动改写。错误已经进入历史时，可用原编辑/删除入口修正对应消息及派生总结，再继续。

这次改善的是**语义归属说明与执行证据**。程序本来就固定以角色发送；它无法只凭一串文本判断模型是否把玩家台词挪给了角色。同一句“到宿舍了吗”可以由双方说，因此不能用文本相同或“发微信”关键词做可靠的万能拦截。回执身份也不能证明模型选对了台词。真实模型仍可能违背规则，不能据假 API 测试承诺幻觉比例已经下降。

调试时在 Console 筛选 `[模型请求]`，查看最后 system 中 `<wechat_sender_boundary>` 的双方姓名和可用工具，再查看 `tool_wechat` 原生参数与工具回执的 sender/recipient。如果错误仍出现，可据此区分「生成前归属错误」与「执行身份错误」。
