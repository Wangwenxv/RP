# RP 真实模型验证与来源边界

日期：2026-11-08。测试模型 `qwen3.7-plus`，`temperature: 1`。用户授权临时测试服务、多次验证，并确认地址与密钥不变、服务可能不稳定。角色卡、personality、世界书原文及原 UI 保留。

## 已确认的结论

真实返回证明：**仅增加开头 system 禁令并不足以稳定避免玩家代写。** 原始请求对照继续补写玩家入住、洗澡、睡觉或微信；初版镜头规则也出现过这些错误。不能根据本地假 API 回归通过，就宣称真实模型幻觉消失。

当前采用两层运行时控制：完整角色职责仍集中在原 system，另外把短 `<rp_turn_task>` 放在最新真实玩家输入之前。短任务判断的是**输入末尾仍待 NPC 回应的当前互动**，不是“输入中是否出现过 NPC 台词”。玩家已经完整报告的同行、对话和行动作为既定事实承接，不自动成为下一段继续代写玩家的授权。

新规则仍是概率约束；真实样例中仍有模型违反规则。结果需按有效返回逐项核对，不能称为硬性拦截、零幻觉或稳定提升的总体错误率。

## 实际结果

各阶段共保存 **32 份有完整最终文本或角色工具调用的有效返回**，另有 **59 份错误请求记录**（主要是服务 HTTP 402；含部分已得到地理中间结果但未完成最终回复的请求），无截断结果。一次短 `OK` 服务探测另计，不是 RP 语义验证。失败重试的 HTTP 尝试也单独记录，不把未发出的队列算进这些数字。

最终磁盘规则有 **11 份有效结果**；请求与当前构造器逐项 hash 对照一致，角色/personality、世界书、摘要、RP原文和相应玩家输入均未改写。

初始9000上限的原始请求有3份有效返回，3份都新增了玩家入住/洗漱/休息等行为。最终规则改用4096上限；相同4096上限的原始对照未成功完成最终文本，**因此不据此计算前后幻觉率的统计改善**。以上只是有限样例的逐项事实，不是大样本实验或同上限的完整配对结果。

`evaluation-summary.json` 存有具体样例ID与判读。代表性未解决失败是 `original-reviewed-05`：仍补写玩家掏手机，并编出晚上十一点“我到了，你专心弄，不用回”的旧微信；`original-reviewed-07` 又编出“我和师姐走啦，你弄完早点休息”。不能把这些结果算作完整通过。

本次没有修改角色内核、降低温度、自动删除模型正文或默默给产品每轮增加一笔复核API请求。若要进一步提高可靠性，下一步更适合评估可选的独立复核/重生成：只带有来源的玩家事实与通信记录，核对具体越界句后再重写。这会增加请求次数、延迟和误判处理；当前尚未实现或验证，不能把它当作本次已具备的能力。已有错误正文及由它生成的旧记忆需要用原编辑/重新生成入口修正，新提示不会自动清理这些历史污染。

## 来源与时间改动

1. `built-in-content.js` 的 `<history_source_boundary>` 区分微信原消息、RP 当面经历、摘要/记忆。摘要只支持明确事件的大意，不还原为逐字聊天、照片、配文、表情包或已读状态。玩家明确提供的已发送原话按其原方向承接。
2. `26-recap.js` 给三类临时背景分别标记 `_storyArchiveKind: summary / rp_originals / wechat_originals`。`data-services.js` 标准化保留类别、不同类别不合并；`15-generate.js` 在内部组装中保留类别，在 API 字段白名单映射时剔除。
3. 短任务根据真实内部类别指出是否单列过历史微信原文。普通玩家输入提到“微信”，不能被当作微信档案。未提供旧原消息时保持事件概述；需要具体细节且已有原文检索工具时先核实，查不到省略该细节，仍可创作 NPC 当下的新生活。
4. `<current_turn_frame>` 只从真实玩家原文中独立成行的完整公历时标取当前时段。使用现有剧情钟校验，不取现实日期、摘要、世界书、引语或代码块；未闭合代码块中的时标也忽略。无可靠时标时不制造日期。仅作为请求提示，不写回剧情钟。
5. 主生成管线显式传入最后真实玩家原文，避免世界书插入或微信回灌里的日期误作玩家本轮时标。切镜头不把历史中已经发生的离开/返宿重新发生在当前时间。
6. 微信只生成角色自己的新发送；不得先编一条玩家来信触发回应。一次真实角色联系后停止 RP 自动续写，由玩家回答。没有联系动机仍可继续 NPC 事务。

## 实验方法

原始素材是本地忽略目录的 `card/suqixue/tmp.txt`、`tmpres.txt`。请求共 11 条 messages，45,822 个 JS 字符，最后玩家原文 338 字。该数字不是 token 数。原始请求中没有完整工具 schema、流式及输出上限等参数。

- 对照保留人物资料、世界书、提要、RP 档案和真实玩家原文；只替换运行时 system、受管预设及固定准备对话中的对应控制内容。最终另插一条短 system，不改玩家消息内容。
- 各阶段都使用 `qwen3.7-plus / temperature: 1`。初期输出上限为 9000，后期为 4096；只在相同上限内作直接比较。服务返回 `finish_reason: length` 的结果算截断、不算通过。服务实际 usage 按原返回保留。
- 两组统一使用工程当前 `tool_wechat` schema 和本地 `tool_geo` schema。由于原快照缺少 schema，这不是原服务完整参数的精确复现；测的是固定公共工具条件下的控制差异。
- 微信调用只在隔离评测中记为模拟排队，不写用户真实微信时间线，不合成玩家回复，不继续请求 RP。多次联系单独记错。
- 地理使用工程本地查询库，只依据明确当前输入重放定位；混合档案无法还原的结构化位置保持未知，不伪造 GPS 或路线结果。其他未提供的执行器返回不可用。
- 原请求没有原文检索 schema，本次对照没有偷偷添加检索工具。工程内检索和记忆的实际接线仍由现有设置决定，见 [请求调试与检索](./history-retrieval-and-debug.md)。
- HTTP 402 `insufficient_user_quota`、网络失败、截断、工具轮次耗尽均单列。用户确认服务可能不稳定后，允许有限重试，不更换模型、不降温、不把拒绝算进语义成功率。

检查正文中的新增玩家言行/内心/发送、镜头选择、虚构旧通信、跨场景知情、角色工具方向、一次联系后交接、直接互动及指定代写是否保留。不能仅凭关键词未出现、模型自行声称遵守、思考中的承诺或工具调用存在就判通过。

## 证据保存与复跑

原始请求、完整服务响应、原生 reasoning、usage、finish reason、工具参数、执行结果、请求 hash 和手工判读均存放在忽略目录 `.refactor-tmp/rp-live-eval/`。内容包含私人角色与剧情，不提交到 Git。阶段命名是实验标签，不能把某个叫 `final` 的中间候选误认成最终磁盘代码；按请求中短任务、来源状态和源文件 hash 对照。早期 REPL 有两次使用了上一版已缓存构造器，相关 `original-reviewed-01/02` 不计入最终规则。

`tools/refactor/live-rp-eval.mjs` 可复跑保存的完整请求 JSON。凭据只从调用参数或 `RP_TEST_API_KEY / RP_TEST_BASE_URL` 环境变量读取，不写入证据，也不通过命令行传入。

```powershell
node tools/refactor/live-rp-eval.mjs .refactor-tmp/rp-live-eval/reviewed/original-reviewed-03.json .refactor-tmp/rp-live-eval/repeat 4 3
```

先在当前进程安全配置上述环境变量。脚本默认输出上限 4096，并发上限 3；可从模块调用设置每个任务的上限和有限重试，重试上限 2。连续三次鉴权/套餐拒绝后停止剩余队列。未运行案例列在 summary 的 skipped，不冒充已请求或失败语义样例。正式复跑新版本时，应先从新 Console 导出新请求，旧证据不会自动更新为新代码。
