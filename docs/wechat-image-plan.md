# 微信图片回复方案

本文件记录设计取舍；第 1–11 节保留实施前的分析和建议，第 12–14 节记录已确认方向及后续调整。第一版已实现相册、程序绘图、短描述历史及按需查看原图，当前行为和验证见 [实现交接](./wechat-and-RP.md)。前提是用户目前没有生图 API，
希望角色既能按请求发图，也能在合适的时候自己发图；图片能力不能只有付费生图一条路。
微信与 RP 可以共享底层图片能力，但微信的发送策略应独立于 RP 的“每轮自动插图”。

## 1. 建议先确定的方向

把“角色想发什么图”和“系统如何取得这张图”拆开：

```text
同一轮微信模型判断：能否通信 → 是否想回应 → 是否想发送图片 → 图片用途/内容
                                  ↓
图片执行器：本地图库 / 程序绘图 / 联网找图 / 可选生图服务
                                  ↓
真正取得图片并保存 → 发出图片气泡 → 历史只保留图片引用与短描述
```

第一版建议先做 **本地图库 + 程序绘图 + 图片短描述记忆**，没有生图 Key 也可以用。
联网图片检索作为下一步；现有 RP 生图服务作为可选适配器，未配置时不暴露给微信模型。
本地图库也可以由项目附带少量经过整理的素材，避免用户必须先上传才有图可发。
附带素材的实际选择、整理和许可确认属于实施工作；第一版已经加入三张整理后的素材，见实现交接及素材目录 README。

这里的“低成本”指不新增图像生成费用。聊天模型原本的请求仍有成本；
找图、识图、二次挑图若使用服务也可能收费，不能把它们统称为免费。

## 2. 实施前代码基线：已经有什么，缺在哪里

下表描述图片功能实施前的代码，用于解释设计依据，不代表第一版完成后的状态。`ARCHITECTURE.md`、`MODULES.md` 部分行数/旧描述早于当前迭代。

| 链路 | 实施前行为与判断 |
| --- | --- |
| 微信模型调用 | `25-wechat.js` 的 `requestWechatReply` → `05-state-editing-export.js` 的 `requestTrackedChatCompletion` → `api-utils.js` 的聊天端点。一次请求返回 JSON，微信本身没有工具续写循环，也没有给该请求传入 RP 的原生工具表。 |
| 回复协议 | `wechat-protocol.js` 的 `normalizeMessages` 只承认 `text/sticker`，其他类型降成 `text`，并且先检查非空 `content`。因此仅在 prompt 里要求发图、或新增模板 `<img>` 都不够；图片意图必须有新的解析契约。 |
| 用户发图 | `sendWechatMessage` 将图片 dataURL 存到 `{ role:'user', type:'image', content:... }`。`buildWechatModelMessages` 将窗口里的用户图片作为 `image_url` parts 发给当前聊天模型，依赖其识图能力。 |
| 图片气泡 | `index.html` 的 `.wx-root` 已按 `item.type === 'image'` 渲染 `<img>`，没有限制只能来自 user。显示角色图片有基础，但资源取得、引用解析和发送状态还没有。 |
| 表情包 | 模型只看名字/短描述目录，前端匹配真实图片；微信/RP 历史只带 `[表情 名字]`。这种“模型选语义、前端取资源”的分工可以借鉴，照片仍需独立资源 ID 与画面描述。 |
| RP 生图 | `built-in-content.js` 提示输出 `image###英文Tag###`；`20-character-crud.js` 的生图正则把标记转成图片卡片；`07-image-gen-autosave.js` 提交 `/api/jobs`、轮询、把结果贴到 DOM。它确实依赖外部生图服务，不是浏览器自己画出照片。 |
| 生图耦合点 | RP 开关挂在“自动生图”世界书，默认要求每轮 2–8 张插图。`07` 的任务还绑定卡片 DOM、任务 Map 与轮询。不能整套搬到微信，否则会继承正文格式、强制频率与不适合微信的执行方式。 |
| 联网工具 | `17-retrieval-web-tools.js` 的 Tavily 搜索要求 `tavilyApiKey`，当前请求没有图片检索参数，结果只映射网页文字/URL/favicon。favicon 是网站图标。已有联网搜索不等于已有微信图片搜索。 |
| 微信历史预算 | `WECHAT_HISTORY_LIMIT = 30` 限制的是合并后的历史条数；单条长文字不截断，用户图片不合并。最新未覆盖 RP 块有保留机制。30 条限制既不是 token 上限，也不是内存上限。 |
| RP 与摘要里的图片 | `buildWechatRpSegment`、`26-recap.js` 的 `formatRecapWechatLine` 对图片都只输出 `[图片]`。后续 RP、压缩素材和保留的微信原文不知道图片到底是什么。 |
| 长期记忆 | 微信读 RP 的最近 10 份未被前情提要覆盖的经典记忆；微信回复不会自动进入 `16-memory-extraction.js` 的经典记忆抽取。微信图片的长期承接应先接入 `26` 的统一提要，不要假设现有经典记忆会自动收录。 |
| 存储/加载 | 当前 `wechat_timeline` 整体载入内存，`saveWechatTimelineNow` 克隆整条时间线再保存。图片内嵌 dataURL 时，聊天变长会增加读取、复制、写入与图片解码的负担。缩短模型窗口不能解决这件事。 |

## 3. 没有生图 API 时的几条路径

| 图片来源 | 适合什么 | 新增成本/条件 | 主要限制 | 建议 |
| --- | --- | --- | --- | --- |
| 本地图库 | 饭菜、书桌、窗外、宠物、花、手作，以及为某个角色准备的固定形象/相册 | 可离线；无生图费用；先准备素材与标签 | 画面选择有限，不能随意改人物、服装、物品 | 第一版主路径，最容易得到可控照片 |
| 浏览器程序绘图 | 小纸条、爱心、简笔画、路线示意、便签、人物画给对方的小图 | 使用当前聊天模型输出少量结构参数，浏览器渲染；无额外生图请求 | 适合图形，不适合逼真的随手拍/人物自拍 | 第一版主路径，能让角色主动表达 |
| 公共素材检索 | 找某种花、食物、风景、动物的参考图 | 需联网；可选不需 Key 的公共图片目录/API | 搜索相关性、网络、CORS、图片可用性与许可都需要验证 | 第二步；作为找图能力，不能保证精确还原当前场景 |
| 已配置的搜索服务 | 更开放的图片检索 | 服务可能要 Key/消耗额度 | 当前 Tavily 工具还需扩展图片结果适配；不能直接把网页结果当图片 | 可选；先核对服务契约再实现 |
| 外部生图服务 | 任意新场景、构图变化、复杂插画、较一致的角色形象 | 生图服务/Key/额度；参考图一致性取决于服务能力 | 等待、费用、失败与画面偏差 | 留适配口，当前无 Key 不启用 |
| 本机图像模型 | 不走付费云端也生成新画面 | 需安装模型、显存、算力与本机服务 | 内存与维护成本大，尤其不适合为本次功能先加一整套运行环境 | 后续高级选项，不作为最小版前提 |

**普通文本模型能够设计图形，不能仅靠文字响应凭空产出任意逼真照片。**
它可以给浏览器一个场景描述、SVG 或绘图参数；真正生成图片的是渲染器。
图形复杂度应限制在可稳定执行的范围内。所谓“没有生图 API”，仍可依靠本地渲染和已有照片，
不意味着照片的视觉信息不需要来源。

一些成本低、又符合微信习惯的具体能力：

- 角色画一张“今天也要好好吃饭”的纸条，或者一个歪歪扭扭的小人，主动发给对方。
- 从角色相册选一张宠物/花/窗景，发“刚翻到这张”；老照片可以确实是老照片。
- 饭菜、桌面、窗外等不露脸画面优先做素材匹配，降低人脸、服装与身份的一致性要求。
- 以已有素材做裁剪、拼贴、加手绘标注，得到便签式图片；记录它来自哪张图，不声称获得了新角度。
- 保存角色此前发过的图，之后允许“再发一下刚刚那张”，直接复用同一资源，不重新找图或生成。

不建议把随机照片服务当作可靠的按语义找图，也不把临时网页抓取/搜索站页面爬取作为最小版基础。
“返回了一张图片”不足以保证符合剧情。

## 4. “在干嘛 → 吃饭 → 拍个照”怎么处理

角色先判断能不能拿手机、是否愿意拍给这个人看。这与 [迭代历史](./wechat-iteration-history.md) 第 5–6 节的沉默规则一致；
“拍个照”不是程序强制发图的关键词，睡着、无法通信、拒绝分享时仍可以空回或按人设文字回应。
角色也可以在本轮主动选择发图，例如聊天提到猫，确实想给对方看自己保存的猫图。
主动指当前微信回合自主选图；没有新增后台定时发图或自动推进剧情。

能回应且愿意发时，按图片用途处理：

1. **已有确切饭菜/地点设定**：先找匹配本地素材。已说吃面，不能因为图库只有米饭就换成米饭；
   画面背景也不能把宿舍变成餐厅。实在没有匹配资源时，不能拿一个不相符的图硬交付。
2. **只说了“吃饭”，细节尚未建立**：可选择合适的饭菜素材作为虚构场景的视觉补充。
   若允许这种玩法，发送后短记录要固定本次画面，下轮“这是什么菜”才能接得上。
   系统不能把素材附带的拍摄地点、作者、日期自动变成角色的剧情事实。
3. **没有照片，只有绘图能力**：可以按人设发“给你画个简易版”等文字和一张小图，
   但这是画图回应，不等于已经完成了真实照片级的“拍个照”。也可以只用文字回应。
4. **搜索到类似饭菜**：可以发参考图；将其当作虚构场景镜头使用需要匹配剧情并明确设定使用方式。
   不能把搜索到陌生人的自拍绑定成角色本人，或者把参考图当作任意当前场景的证据。
5. **以后配置了生图服务**：才可以尝试按当前场景生成新画面；成功后再发。
   生成也会偏离要求，所以 prompt 不等于照片实际画面。

这里有一个需要讨论的体验选择：是否接受**素材扮演虚构场景照片**？
它能低成本覆盖吃饭、桌面、窗景，但与精确还原同一个人、同一处房间、同一套餐具是不同的要求。
建议用素材承担不露脸、约束较少的场景；人物自拍优先使用角色专属相册，
同一场景换角度/换姿势留给更强的生成服务。来源信息保存在资源详情，聊天气泡保持自然。

## 5. 程序绘图：Canvas 不会自动把源代码传回模型

`canvas.toBlob()` / `toDataURL()` 导出的是像素图片，包含格式头和编码后的图像数据，
不是绘图 JS、HTML 或 SVG 源码。模型只收到代码，是因为应用把代码保存为正文并重新拼进了请求，
不是 Canvas 的传输行为。现在的 `compressImage` 本身已经使用 Canvas，微信发送的是它导出的图片。

第一版建议采用 **模型给结构参数，项目自己的渲染器画图**：

```json
{
  "messages": [
    {
      "type": "image_request",
      "media": {
        "mode": "draw",
        "template": "note",
        "text": "记得好好吃饭",
        "decorations": ["heart"],
        "tone": "warm"
      }
    }
  ]
}
```

以上是**待实现的新协议**。`image_request` 是执行意图，不能直接落成气泡，
`template/tone/decorations` 是渲染器支持的枚举，文字长度、画布尺寸、元素数量都有上限。
模板负责自动换行与布局，浏览器负责导出 PNG/WebP。实际模板、参数名和上限在实施时定稿。

第一版不需要让模型写任意 JS，也不复用当前 RP 的可执行 HTML/iframe 渲染来生成微信图片。
现有正文渲染能保留 HTML 源文本，直接把绘图页面塞到正文会增加后续上下文负担。
若后续允许自由 SVG，可以在隔离的渲染步骤中限制其功能并栅格化；源码仅作可选调试资料，
正常历史投影仍只输出“手绘纸条：记得好好吃饭，附一个爱心”。

绘图参数会占**本轮输出**的一些 token，但执行后不应在后续每轮重放。
把它换成短描述与资源 ID，既能记住画了什么，也能避免反复传源码。

## 6. 联网找图：与聊天模型分开的资源检索

可以新增 `ImageSearchProvider`，输入检索词，返回少量候选：

```text
候选 ID、短标题/描述、缩略图 URL、来源页、许可信息
```

不把整张网页、HTML、全部搜索结果或图片 base64 塞给角色模型。
先在前端/服务适配器按已有标签筛选；只有搜索歧义较大时，才可选增加一次短候选选择请求。
模型输出候选 ID，程序检查它确实来自本轮结果；不能让模型凭空编图片 URL。

可评估 Wikimedia Commons 等公共图片 API 作为不需生图 Key 的来源。
本次做了一次 Commons 只读元数据请求，**20 秒超时，没有取得有效响应**；
因此本节只把它列为候选，尚未确认用户当前网络、`file://` 与静态部署下的跨域和图片下载链路可用。
搜索服务/参数契约的进一步核对也属于实施前验证，不能在本次文档里宣称免费检索已打通。

即使远程 `<img>` 能显示，也不等于 `fetch` 或 Canvas 能读取它的像素。
要压缩、缓存或识图，需要源站允许跨域；跨域绘制可能让 Canvas 无法导出。
第一版应优先使用经过验证的来源，并缓存成功取得的图片。
只留外链可以降低本地磁盘占用，但会产生离线失效、链接过期等问题，不能算成本全无的替代。

本地图库也需要“少量候选”机制：小图库可按标签全部匹配；图库变大后只注入约 3–6 个候选的 ID 与短描述，
不把完整目录每轮塞进 system，更不复制表情包目录的固定前 50 条模式作为照片检索。
第一版可用标签匹配，无需为几十张图先引入向量数据库。

## 7. 新协议与执行顺序：成功拿到图才算发图

保留现有 `messages` 数组、`messages:[]` 和 `silence`；新增一种有效的 `image_request` 消息意图。
本轮可只有图，也可“文字 → 图 → 文字”，仍按数组位置播放。每轮图片建议先限 1 张，
属于技术预算，不要求每轮都发，也不受表情包概率裁剪。

本地相册例子（候选 ID 必须由程序提供）：

```json
{
  "messages": [
    {"type":"text","content":"给你看看"},
    {
      "type":"image_request",
      "media":{"mode":"album","assetId":"meal_noodles_01","usage":"scene_photo"}
    }
  ]
}
```

`usage` 可区分虚构场景配图、旧相册照片、参考图、绘图等用途；准确枚举待实现时确认。
`mode` 只能来自本轮可用能力列表：没有生图配置不允许 `generate`，离线不允许 `search`，
图库为空不给不存在的相册候选。程序仍要校验，不能只依赖模型遵守提示。

执行建议：

1. 复用同一次微信模型请求输出文字/沉默/图片意图，不另加一个每轮“要不要发图”的判断请求。
2. 解析器先按类型分支校验：合法图片意图即使没有文字 `content` 也有效；非法结构报告失败，
   禁止沿用“未知类型转文字”把 JSON、SVG 或 URL 当普通微信发出去。
3. 执行器解析素材或绘制；必要时才搜索/调用已配置生图服务。等待状态是应用的任务状态，
   不能把整个搜图/生图等待期都显示成角色“正在输入”。
4. 成功取得可显示图片、写入资源后，在数组对应位置追加实际 `type:'image'` 消息。
   这才计入微信消息数、清零连续沉默，并参与提要覆盖；图片意图/任务不算已发送消息。
5. 失败/中止/切 scope 不追加成功气泡，也不记成主动空回；保存失败状态和重试入口。
   只有图的回复失败时，用户发言仍待处理；若已有文字发出，图片任务要有独立重试入口，
   不能只依赖 `wechatUnansweredCount`，否则文字已让计数清零。
6. 文字若明确依赖图片（“这就是那碗面”），连同该图准备成功后再播放，避免留下没有图片的断言。
   可独立的前置短文字可以先发；重试只补失败图片，不重播已发送文字。
7. 复用中止与 scope 校验，增加任务 ID/请求代次，校验角色、分支、触发消息与当前 controller。
   切走再切回同一 scope 时也不能让过期任务重新出现；不只检查 scope 字符串。

失败不能静默把“拍照”换成“涂鸦”，或把人物自拍换成无关网图。
降级必须保持原用途；改变用途时可选让模型再组织一句符合人设的说明，这是异常路径的额外请求，
正常本地图/绘图不需要第二次聊天请求。

RP 主动 `tool_wechat` 当前只接收非空 `content` 字符串，不能假设新微信协议会自动接上。
第一版先支持微信回合的请求发图/自主发图；之后单独扩展主动工具的结构化参数与待发送队列。
RP 整轮成功后才 flush 的时序继续保留，避免微信图片任务打断 RP 正文。

## 8. “内存”要分别控制三件事

**A. 浏览器内存：不要每次开微信就加载所有图片。**

- 时间线只放文字、消息元数据、资源 ID 和短画面描述；图片二进制分开保存，按可见范围加载。
- `loading='lazy'` 现在已有，但完整时间线 dataURL 仍在内存、DOM 仍遍历全部气泡；
  真正降低长期聊天压力还需要图片按需读取、缩略图，以及较长历史的显示窗口/分页。
- 限定正在处理图片的数量、像素总数、文件大小。压缩文件小不等于解码占用小：
  1024×1024 的 RGBA 像素约 4 MiB，解码图、Canvas 和导出过程还可能同时持有多份数据。
- object URL 只用于当前显示，离开显示范围/切 scope/关面板时回收；不能持久化 `blob:` 地址，刷新后应重建。
- `07` 的任务 Map 和 DOM 卡片引用需要有生命周期清理；共享资源服务不能长期持有整段聊天的 DOM。

**B. 本地存储：图和聊天分开写。**

- dataURL 的 base64 部分通常比压缩二进制多约 1/3；JS 字符串实际占用取决于引擎，
  不能把 base64 长度直接当作实测内存。建议新资源保存 Blob，时间线保存 `assetId`。
- 资源可以使用现有 IndexedDB `store` 内的独立键，先不新增 objectStore；资源索引与资源二进制分开。
  这只是建议，新增专用 objectStore 则需要数据库版本迁移。
- **现有 `cloneForStorage` 不能直接拿来克隆 Blob**：`unwrapForStorage` 会把一般对象按可枚举属性展开，
  没有 Blob 分支。应由专用资源服务使用支持 Blob 的存储路径，避免先被转换成空对象；
  不依赖 JSON 克隆兜底。资源和消息的成功状态以事务完成为准，必要时原子提交。
- 缩略图建议长边约 256–384，聊天图约 768–1024；纸条保留清晰文字优先使用 PNG/WebP，
  照片使用 WebP/JPEG。是否保存全尺寸原图由容量设置决定。
- 相同素材复用 ID，不因再次发送而复制一份；清理未被任何保留记录引用的临时资源。
  用户保存的相册素材与临时任务缓存分开管理，清空某段聊天不能顺手删掉共用相册。

**C. 模型上下文与记忆：不要每轮重看全部图。**

- 默认发给聊天模型的是 `[图片｜晚饭：白碗面条，桌边有一杯水]` 之类的短描述，
  正常历史不包含 dataURL、源码、搜索网页、完整绘图参数和生图英文 Tag。
- 新的用户图片可按需送视觉模型识别一次，再保存短描述；主 RP 已有 `visionModel` 与识图描述管线可参考。
  没有视觉能力时不能凭空补描述，显示“图片尚未识别”并保留后续查看路径。
- 自己绘制的图可由渲染器根据实际参数生成描述；整理好的相册使用经过核对的素材描述，
  不需要每发一次再识图。搜索图/生成图不能直接把搜索词/生成 prompt 当成实际画面事实。
- 用户追问颜色、小字、具体数量等短描述未覆盖的细节时，再按资源 ID 重看选中的图。
  建议最近/指定视觉附件最多 1–2 张，超过预算改用摘要；具体预算按所用模型调整。
- 用户图片的识图结果仍遵守 [迭代历史](./wechat-iteration-history.md) 第 6 节的感知边界：系统识别不等于角色当时已读，
  `unseen/noticed` 的历史不能因图片有描述就变成角色知道全部内容。
- 不默认给历史 assistant 消息附 `image_url`：部分聊天接口只支持 user 图片输入。
  默认使用 assistant 短图片记录，需要重看时交独立视觉请求，保持原发送者和时间位置。
- 图片视觉 token 由具体模型的尺寸/detail/计费方式决定；用 URL 代替 base64 主要减小传输，
  不保证省视觉 token。图片塞在普通字符串里则会变成无用文本负担。

当前 30 条消息预算继续保留，但应补充图片数/像素预算与文本体积预算。
先保护本轮用户发言、最新有效 RP 处境、连续沉默状态和必要图片描述，再压缩更早历史。
不切半句或直接删除持续状态来腾空间；较长内容应通过已有统一提要承接。
前情提要压缩的是模型输入，不删除图片二进制；磁盘清理由独立资源策略处理。

## 9. 图片记录：记住图里有什么，不记工具怎么跑

建议实际发送后的消息大致为：

```json
{
  "id": "wx-message-id",
  "ts": 1790000000000,
  "channel": "wechat",
  "role": "assistant",
  "type": "image",
  "content": "",
  "media": {
    "assetId": "media-id",
    "source": "album",
    "usage": "scene_photo",
    "caption": "晚饭照片：白碗面条，桌边有一杯水",
    "captionSource": "curated"
  }
}
```

以上是建议数据结构；空 `content` 由新的资源解析器提供显示地址，不能直接套进当前 `<img :src="item.content">`。
旧 `type:image + content:dataURL` 保持兼容，可在需要读取/保存该图时渐进迁移，
不要为上线先把所有历史图片全量解码。
资源表保存 Blob、尺寸、缩略图、原始来源/许可、可选服务任务 ID；正常模型请求只投影用途和画面描述。
短描述建议约 40–100 字，详细视觉描述可另存，按需读取，不必每轮注入。

至少统一三个投影出口：

- 微信上下文：assistant 图片保持在它原本发送的位置，写成“你发送了晚饭照片：……”，不合并成用户发图。
- RP 回灌：`林晚：[图片｜晚饭：白碗面条，桌边有一杯水]`，让后续面对面聊天能承接。
- 压缩素材与保留原文：相同短描述，让提要能记成“林晚发来晚饭照片，双方聊到面条”，
  只保留对剧情有意义的视觉细节，不展开每张图的完整识别文字。

`captionSource` 区分整理素材、确定性绘图参数、视觉识别、未经核对的生成意图等来源。
存了生成请求不代表图中确实出现了所有要求；识图不确定之处保持不确定。
发送成功是故事中的新行为，但图片拍摄时间/地点、角色正在做什么，不能只靠资源作者元数据推断。

## 10. 与当前 RP 生图的关系：共享服务，微信单独决策

建议以后抽出不依赖 Vue/DOM 的图片任务接口：

```text
resolveMedia(intent, { capabilities, scopeId, requestId, signal })
    → { assetId, caption, source, usage, dimensions }
```

执行器分派到 `album/draw/search/generate`。微信只消费结果；RP 图片卡片也可逐步消费同一服务。
对于现有 `/api/jobs`，可复用提交、查询和内容取得的概念，但要补 signal、超时、失败分类、任务清理和资源缓存。
不能直接依赖 `loadGeneratedImageCard` 这类 DOM 函数完成微信发图。
它目前的任务请求还包含特定服务参数，不能假设任意生图 API 都支持；以后换服务应写独立适配器。

微信默认不继承 RP 的每轮 2–8 张图、`image###` 正文标记或画师配置要求。
可以共用用户已配置的生图 Key/服务，但增加微信自己的允许来源与单轮数量限制。
没有 Key 时，`generate` 不在能力列表中；本地图库、绘图继续使用。
“共享底层”不要求第一版就重构全部 RP 生图 UI，微信先接独立资源执行器即可。

| `data-services.js` | 专用 Blob 存储/事务支持；通用文本上下文后处理当前会 `String(content)`，不能把多模态数组直接塞入该路径 |

资源若跨分支共享，只共享字节，不共享未来消息/当前状态。图库可按角色管理，
临时发图意图按剧情 scope 隔离；删除一个分支不能删掉其他分支仍引用的图片。
先确认现有微信分支继承语义，再决定资源引用复制范围，不顺便更改全部剧情分支行为。

最小验收应包含：

1. 无生图 Key：从已整理的图库发图、绘制便签、只有图片回复、文字/图片混合回复均可用。
2. “吃饭 → 拍个照 → 这是什么菜”能承接已发画面；无匹配素材时不发送错图。
3. 有合适动机时模型可以自主发图；“好的”仍可空回，通信受限不会被发图请求解除。
4. 失败、中止、切分支、切走再切回、刷新后重试不串 scope，不出现假成功，不重复已发文字。
5. 刷新后图片可恢复；默认聊天请求、RP 回灌和压缩请求里有短画面描述，
   没有 base64、JS/SVG 源码、完整搜索结果或大段生成参数。
6. 老的用户图片/表情包/空回记录兼容，感知边界、时间顺序和提要覆盖计数保持正确。
7. 用较多张大图检查按需加载、像素预算、资源回收、存储失败；不只验证“一张图能显示”。

初步方案阶段仅阅读代码、撰写方案及验证原有空回基线（32/32），公共图片 API 的只读探测超时。
后续第一版已完成本地素材、绘图与图片记忆实现；最新测试与真实服务边界统一见 [实现交接](./wechat-and-RP.md) 第 8 节。界面沿用项目现有微信样式。

## 12. 已确认方向与后续扩展

用户已认可素材扮演虚构场景的方案；下列取舍作为后续扩展依据：

1. **真实感目标**：先接受素材扮演不露脸的虚构场景镜头，还是所有“刚拍的”都必须精确匹配当前场景？
   前者适合低成本第一版；后者需要更丰富的专属素材或生成能力，不能承诺 Canvas 解决。
2. **第一批图片用途**：建议先做饭菜/桌面/窗景/宠物相册 + 便签/爱心/简笔画，
   暂时不追求人物自拍、同一房间换角度和任意复杂场景。
3. **联网与付费策略**：建议本地图/绘图默认可用，公共来源检索可单独启用，
   生图通道可选且没有 Key 时禁用；普通发图不默认触发额外识图或第二轮挑图请求。

按这个范围，第一版就能让角色“有图可选、会画小图、记得自己发过什么”，
之后再根据实际使用中的缺口增加搜索来源与生图服务。

## 13. 已采纳：本轮看新图，历史按需查原图

实际消息保存 assetId 与 caption，原图在独立资源库，不内嵌到对话。本轮用户新图完整送视觉输入，后续历史只给短描述；需要核对细节时，tool_view_image(messageId, question) 从本会话取得原图。配置识图模型时由它读取原图回答，否则将像素附到当前聊天模型的工具续写请求。

这控制了重复视觉输入成本；浏览器内存仍由 Blob 独立保存、缩略图、显示窗口与 URL 回收控制。完整指保留画面范围，仍受长边 1600、文件 12 MiB、像素 24 Mi 上限约束，不是原始文件逐字节无损保留。压缩丢失的细节不能凭描述恢复。

## 14. 自然收尾与图片能力按需注入（2026-11-02）

### 14.1 对截图现象的判断

“叮嘱去吃饭 → 好滴 → 去吧／路上慢点 → ok → 乖”暴露的是角色仍然选择发送消息。检查第一版 diff，明确的 `messages:[]` 仍先于图片准备和气泡播放返回，沉默归因和下一轮恢复也仍在；原有 32 项空回测试通过，未发现图片功能把合法空回转成文字的回归。

但原规则允许“亲近、热情或在意对方的人用短句或表情收尾”，没有明确区分首次道别与反复补尾；模型可以把每个确认都理解成再次表达关心的机会。图片第一版又无条件在 system 末尾附发送格式、素材目录、记忆与描述规则，形成额外竞争。因此先修正决策倾向，再减少无关能力的常驻输入。

这里只能确认代码路径和提示词内容，未取得截图对应的完整请求、所选角色/预设及模型输出，不能断言是“上下文太多，模型无暇顾及”。人设示例、选中的世界书与预设、历史里多次接尾及模型本身都可能影响表现；无需据此删减剧情事实或物理约束。

### 14.2 采用世界书触发方式，但不把关键词当成发送开关

复用 RP 世界书匹配器，使用内部图片能力条目；仅扫描本轮尚未处理的用户文字，支持连发。命中“照片、拍个照、发张图、画张纸条”等时，才提供完整来源格式和相册候选。上一轮明确邀请发图、用户本轮接受也加载。所有判断每轮重算，不扫描旧图描述、RP 背景和角色设定，避免图片说明一直挂在后续确认消息上。

仅用关键词会损失两类能力：用户说“在干嘛”时角色自主分享，以及未说“图片”但问“碗是什么颜色”时查看旧图。为此分离三个入口：

- 普通轮保留简短 `tool_load_image_sending` 入口，模型确有动机时取回完整发图说明与目录；加载本身不发送，也可以之后空回。代价是此路径多一次聊天续写，并要求接口支持原生工具。
- 历史有图时保留 `tool_view_image` 和简短记忆规则，细节问题由模型决定是否查像素；不依赖穷举所有描述颜色、文字或数量的关键词。
- 用户新图始终作为本轮视觉输入，缺少 caption 才加描述写回规则；既不靠“照片”一词触发，也不为了省上下文降成猜图。

关键词只决定模型能看到多少发图说明，不能强迫回复、强迫发图或解除人物的通信限制。工具加载结果仅留在本轮请求，不写入历史；原有独立 Blob、缩略图和短描述存储方案不变。

### 14.3 收尾规则与验证边界

规则按用户后续反馈收紧为：话已说完、对方确认或表示暂时离开且无待回应事项时，默认直接 `topic_closed` 空回，不以“先叮嘱或道别一次”为结束前提。只有必要的具体信息补充、新问题或明确情绪诉求才考虑继续；亲近关系、吃饭或出门本身不构成补话的理由，也不设固定概率随机叮嘱。完整图片说明移到回复决策之前，system 末尾放简短决策提醒。接受邀请仍结合语境判断，客户端不按“好的／ok”硬裁模型输出。

回归测试覆盖截图形式的历史输入与空回落库、下一轮新问题、触发后卸载目录、无关键词工具加载、工具后空回、新图经过续写仍完整输入、调用上限及切 scope 中止。一次加载最多加两次查看，总计最多四次聊天请求；通常文字回复或关键词直达发图仍是一轮请求。

测试用单个相册素材时，完整图片提示正文 567 字符，普通无图聊天为 68 字符；这只比较图片说明正文，不包括角色/剧情、工具 schema 或实际视觉 token，不能当成整轮 token 降幅。真实模型收尾效果仍需在同一角色、预设与模型下对照试聊，fixture 通过不能替代语义效果验证。
