## 问题与确认的缺口

用户提供的回复先写苏祈雪发消息等待，随后无玩家输入地写“微信弹出一条新消息，是陈璃发的”，再让她回复、确认并赴约。即使没有展示陈璃消息的具体文字，“陈璃发送了新消息”本身也已经代写玩家行为。COT 中写“没有替陈璃行动”不能证明正文遵守边界。

代码确认的入口有三处：

- 工具说明原先允许想连发多条就多次调用，执行队列也接收同轮多个主动微信。
- `deliverActiveWechatMessage` 与播放流程复用被动回复的宽容解析，一次 content 可含多消息 JSON，解析后发送者等额外字段被忽略，所有气泡按当前角色发送。
- 工具执行成功后统一调用 `generateResponse` 自动续写；发送回执不是玩家回复，却仍给模型机会继续编造收到回复和双方约定。

工具外层参数原本就不接受 `sender/role`，实际气泡发送者一直固定为当前 AI 角色。截图和正文不足以还原该次请求的调用次数、参数或续写分段，不能断言四条消息恰好出自哪个入口；以上是代码中确实存在、能重现的执行缺口。

## 当前行为

主动微信是当前 RP 回合向玩家的交接：

1. 模型可先写角色独立活动，到准备联系玩家的位置。
2. 本轮接受一次 `tool_wechat`：`content` 为当前角色的一条纯文本消息或表情，或用独立 `image` 分享一张图片；两者二选一。复杂画面可用描述卡片，仍只占一个气泡。
3. 同轮第二次及后续主动微信调用返回明确错误，不排队、不落气泡。不接收 content 内嵌套 JSON、消息列表或发送者字段；纯文本换行保持一个气泡。主动图片支持描述/本地相册/手绘，主动语音尚未接入。
4. 同批所有原生调用仍配对执行和结果；只要有成功排队的主动微信，结束自动工具续写，保存当前 RP，然后由原有流程打开微信面板、播放消息。
5. 玩家用现有微信输入框回复，或在下一条 RP 输入中明确回应后，再开始下一轮。没有主动联系的 NPC 事务仍可连贯展开。

这意味着主动联系在每个 RP 回合只发一个气泡。原被动微信收到玩家消息后仍可按原协议分为多个气泡，正常检索、随机数、地理等工具仍自动续写。工具参数错误且尚未成功联系时，也保留原有错误修正流程。

发送函数返回 `queued: true, delivered: false, awaitingPlayer: true`，仅表示成功排队；实际播放仍在整轮 RP 收尾。它不表示已经送达、玩家已读或玩家回答。

## 验证

八组离线回归共 **143 项通过**，玩家决定权浏览器模拟通过，无页面运行时错误。命令：

```powershell
node --test tools/refactor/test-player-agency.cjs tools/refactor/test-wechat-silence.cjs tools/refactor/test-wechat-time.cjs tools/refactor/test-wechat-media.cjs tools/refactor/test-wechat-voice.cjs tools/refactor/test-wechat-documents.cjs tools/refactor/test-memory-recall.cjs tools/refactor/test-full-backup.cjs
node tools/refactor/smoke-player-agency.cjs
```

实际应用管线模拟一次提交“在忙吗 / 图书馆 / 好 / 你早点弄完 别太晚”四个原生调用，仅第一条作为 `assistant / wechat` 进入时间线，后三条返回错误。模型请求仅一次，未调用自动续写；下一轮玩家明确输入回复后，新的角色消息正常发送。混合随机工具及单独随机工具验证表明其他结果没有丢失，正常工具续写仍保留原生签名。

测试使用假 API 和隔离数据库，没有访问用户密钥或真实会话。这证明执行边界，不代表真实 qwen3.7-plus 每次都能遵守正文语义规则。

## 生效与限制

刷新页面即可加载执行修正，无需重新导入卡或重新勾选预设。

程序能阻断同轮多次发送、嵌套气泡展开及发送后的自动续写。对于同一次 API 响应已经写出的违规正文，仍靠明确提示约束；没有使用关键词删文，不能承诺任意模型绝不会把虚构玩家回复写在调用前。

旧错误微信、正文与摘要不会自动改写。已形成错误约定时，用现有编辑/删除入口纠正正文和气泡；如摘要已经把它们写成事实，也需修正摘要后继续。

世界叙事与人物认知原则见 [世界自主叙事交接](./rp-world-narrative.md)，玩家控制规则见 [玩家决定权交接](./player-agency.md)。
