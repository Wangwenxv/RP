## 1. 当前能力

微信是同一段 RP 剧情中的通信渠道，共享角色、关系、场景与记忆。角色可发 0–6 个气泡，按人物能力、意愿和局势决定是否回复；空回保留行为记录，不显示空白消息。

图片回复第一版支持：

- 不需生图 Key 的本地相册：内置沙拉、窗边办公桌、黑白猫；用户可为当前角色添加照片和实际画面描述。
- 不需生图 API 的程序绘图：纸条、爱心、猫、花、一碗饭的简笔画，渲染为真实图片。
- 角色在微信回合自主决定发图，可回应“拍个照”或自行分享。发图说明按本轮关键词加载，关键词不强制发送；没有后台定时发图。
- 本轮新图的完整视觉输入、历史短描述、`tool_view_image` 按需查看。图片气泡可点击放大。
- 可选联网参考图检索、可选现有 RP 生图服务适配；默认关闭，生图无 Key 时不向模型暴露。
- 图片任务持久化与独立重试；失败、中止、切 scope 不会伪装成成功图片或主动空回。

用户认可素材承担约束较少、不露脸的虚构场景配图；不能把不匹配素材、陌生人自拍或来源元数据变成既定剧情事实。

单条消息可编辑/删除：文字气泡可改文案、复制、删除，图片与表情只能删除；改动写回 `wechat_timeline`，气泡、下一轮请求、RP 回灌摘要同时生效。生成中禁止改动；编辑用户消息会作废当时的空回标记，但不会自动请求回复。细节见 [单条消息编辑交接](./wechat-message-editing.md)。

## 2. 使用入口与模型要求

打开角色微信，点击顶栏相册图标查看/发送内置素材。填写名称和画面描述后选择文件，可加入角色相册。与角色聊天即可让模型选择素材或绘图。

微信设置的“图片来源”分别控制联网检索与按需生图。相册与手绘默认可用。生图使用设置中已有的生图 Key，独立于 RP 每轮自动插图的开关和张数。

当前微信请求按需携带图片工具 schema，聊天接口应支持原生工具调用。新用户图片仍要求当前聊天模型支持图片输入。查看旧图时，若配置 `settings.visionModel`，由该模型识别；否则把取回像素提供给当前聊天模型。接口失败不会将短描述冒充识图结果。

## 3. 数据流与代码位置

```text

模型：能力、意愿、局势 → 空回 / 文字、表情 / 图片意图 / 查看工具
                               ↓
图片意图取得资源 → 按数组顺序播放 → 保存真实消息
                               ↓
微信历史、RP 回灌、前情提要：文字 + 短图片描述 + 沉默记录
```

## 4. 回复与图片记录协议

模型输出例子：

```json
{"messages":[{"type":"image_request","media":{"mode":"album","assetId":"builtin-salad","usage":"scene_photo"}}]}
```

```json
{"messages":[{"type":"image_request","media":{"mode":"draw","template":"note","text":"记得好好吃饭","decorations":["heart"]}}]}
```

`image_request` 是执行意图，没有文字 content 也有效，一轮最多一张。来源为 album/draw/search/generate，运行时校验当前可用来源。非法图片结构报错，不降级为 SVG/JSON/URL 气泡。

实际图片消息：

```json
{"id":"微信消息ID","channel":"wechat","role":"assistant","type":"image","content":"","media":{"assetId":"资源ID","caption":"木桌上的蔬菜沙拉","captionSource":"curated","source":"album","usage":"scene_photo"}}
```

`captionSource` 区分整理素材、用户手填、确定性绘图、识图与未核对来源。新用户图片的描述可由本轮模型在信封的 `image_descriptions:[{messageId,caption}]` 中给出，限本轮视觉附件中的消息 ID、120 字；未给描述仍可按 ID 查看，不补写猜测。旧 `content:dataURL` 图片保持可读，新图字节不放进时间线。

## 5. 本轮新图、历史和按需查看

每轮先构造只含短图片记录的历史，末尾附本轮尚未处理的用户新图。最多 4 张，长边最多 1600，文件最多 12 MiB，首次解码后检查像素上限 24 Mi。超预算明确报告，不悄悄截掉本轮图片。完整画面不是原文件的无损逐字节保留。

需要核对旧图时调用 `tool_view_image`：

```json
{"messageId":"历史图片消息ID","question":"上面的字是什么？"}
```

查看工具只允许当前角色、当前分支时间线中的图片，不接受任意资源 ID 或 URL。每轮最多 2 次查看，另允许 1 次发图说明加载，最多 4 次聊天请求（通常无工具时 1 次）；工具结果不落成气泡。续写保留本轮新图，错误明确说明尚未成功查看。

系统识图不等于人物当时已读。历史 `noticed/unseen` 和旧未发送行为保持知识边界，较新的 RP 事实可以改变当下处境。

默认历史、RP 回灌与前情提要不含图片 base64、源码、搜索网页或生图 Tag，格式为 `[图片 #消息ID｜短画面描述]`；查看时才从资源库取像素。

## 6. 上下文、沉默与 RP 衔接

### 6.1 图片说明的触发范围

复用 RP 的 `RPHubContextUtils.resolveWorldInfoEntries` 匹配内部图片能力条目，配置在 `27-wechat-media.js` 的 `SEND_ENTRY`。不往用户世界书写入条目，原有手选世界书仍按选中内容注入。

| 本轮情况 | 发给模型的图片上下文 |
| --- | --- |
| 普通文字聊天或收尾确认 | 简短能力入口与 `tool_load_image_sending`，不查询相册、不注入完整格式和目录 |
| 本轮未处理的用户文字含“照片／拍个照／发张图／画张纸条”等 | 注入发送格式、当前可用来源和最多 6 个候选；不再提供加载工具 |
| 紧接明确发图邀请的“好呀／可以／ok”等接受 | 同样加载发送说明；普通道别后的确认不触发 |
| 本轮用户新图 | 无论关键词是否命中，都附完整视觉输入；缺少描述时才附 `image_descriptions` 写回说明 |
| 当前会话存在历史图片 | 保留短记忆规则与 `tool_view_image`；需要细节时才取像素，不因此常驻发图目录 |

关键词只扫描自最近一次角色回复或主动空回以来的用户文字，包括连发气泡。旧用户消息、图片描述、RP 原文、角色卡和预设不参与关键词触发；接受邀请仅看紧接的角色发言。每轮重新计算，没有永久激活状态。

未命中关键词但角色确实想分享时，可以调用 `tool_load_image_sending({})`，先取得本轮说明再决定发送 `image_request` 或空回。工具只加载能力，不读取图片像素、不发消息；完整结果只存在于本轮请求内，不存入微信时间线、RP 或前情提要。未提供的工具、重复加载及超额查看会报错，不记作主动空回。

### 6.2 自然收尾与空回

`REPLY_DECISION_RULE` 先检查通信能力与意愿，再检查是否还有回复需要。话已说完、对方确认或表示暂时离开且无待回应事项时，默认直接空回，不要求先叮嘱、道别或发表情。只有必要的具体补充（如未交代的约定、需纠正的误解）、新问题或明确情绪诉求才考虑继续；亲密人设不构成例行叮嘱的理由。接受邀请仍要结合上下文判断，不用关键词在客户端截掉模型回复，也没有“按固定概率叮嘱”的机制。

图片说明位于完整回复决策规则之前，system 末尾再放简短 `REPLY_DECISION_REMINDER`。空回复协议与持久化规则保持如下：

- 空回为 `messages:[]`，在本轮最后用户消息保存 `replyDecision:silent` 和 `replySilence:{reason,summary,awareness,decidedAt}`。失败、中止不标记空回。
- 下一轮恢复逐次未发送行为与完整时间线计算的连续次数。次数用于重新判断，不是强制回复阈值；实际文字、表情、图片回复清零连续沉默。

### 6.3 时间线与 RP

- 权威顺序来自角色/分支 scope 的 `wechat_timeline`。RP 块和微信交错还原；连续 RP 转背景块，相邻同 role 气泡合并。
- 微信通常保留合并后最近 30 条；最新未覆盖 RP 块有保留机制，块内最多 16 条 RP 原文；经典记忆最多 10 份未覆盖摘要。这些不是精确 token 上限。
- 前情提要保留摘要、最近 RP 原文、最近微信原文三条独立消息。覆盖计数按真实消息计算，附属图片描述/沉默标记不另增条数。
- `tool_wechat` 是 RP 主动工具，工具与角色开关同时成立才暴露；同轮只接受一条纯文本角色消息或表情，成功排队后结束自动续写，整轮 RP 收尾时 flush。入口拒绝嵌套 JSON、发送者、消息列表及媒体意图；被动微信分段继续使用原协议，见 [玩家交接修正](./wechat-player-handoff.md)。
- 微信通信优先于「剧情面板」：角色决定新发微信且工具可用时，走原生微信工具，不用 HTML 微信气泡或正文虚拟发送替代，也不重复展示已经由工具发送的消息。工具发送方仍固定为当前角色，不能代玩家发送；“玩家尚未发到了”等待行动点留给玩家自行操作，玩家明确说明已发送时可以承接既成事实。规则同时进入内置剧情面板、工具系统提示、续写/规划提醒及工具参数说明；刷新后内置预设按现有同步逻辑更新，旧存档的工具描述也由本轮系统规则覆盖。

## 7. 存储、显示与任务恢复

| 存储键 | 内容 |
| --- | --- |
| scoped `wechat_timeline` | 真正发送的消息，图片保存 ID 和短描述 |
| scoped `wechat_media_tasks` | 未完成的批次、任务 ID、完成位置、失败信息、已取得资源；没有图片字节 |
| global `wechat_media_index` | 轻量索引；用户相册按角色 ownerId 筛选 |
| global `wechat_media_blob_资源ID` | 独立图片 Blob |
| global `wechat_media_thumb_资源ID` | 独立缩略图 Blob |

Blob 使用 `{clone:false}` 路径，避免 `unwrapForStorage` 将其当普通对象展开；写入以 IndexedDB 事务完成为准。内置照片随静态文件分发；file:// 模式按需加载固定像素脚本，避免本地图片污染 Canvas。这些静态资源不会进入聊天上下文。

默认显示最近 80 条微信消息，可查看更早记录；气泡用缩略图，最多同时读取 4 张，点击读取大图。关闭、切 scope 或图片离开显示窗口时撤销 object URL。二进制保存在资源库，缩短模型上下文不会删除原图。删除角色会回收该角色的图片索引、原图与缩略图，保留其他角色资源和内置素材。

单条编辑只改 `wechat_timeline` 里的那一条并立即落盘：被编辑的消息带 `editedAt`；编辑用户消息会清掉该条的 `replyDecision`/`replySilence`。删除单条消息不回收资源库原图，只移除消息记录；若删除落在前情提要的覆盖段内，`coversWechatCount` 同步减一（见 [单条消息编辑交接](./wechat-message-editing.md)）。

图片批次准备成功后才播放依赖文字。失败有独立重试；任务消息用稳定 ID 去重，重试只补未完成部分，并重新确认缓存资源存在。刷新发现未完成任务时显示失败/重试状态，scope 与请求代次共同阻止过期任务落入新会话。

备份导出与分支继承沿用原行为，当前没有新增完整微信图片备份流程；不要把 RP chat 导出当作包含全部微信图片的备份。
