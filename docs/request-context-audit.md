## 为什么提要使用 user

这是工程的组装选择：摘要和最近原文作为输入资料，保留 `role:'user'`。传输层的 user 也承担背景输入，不必等同于世界里的玩家发言。人物说过什么、谁发微信、哪些事实已发生，应由资料来源与真实记录决定。

把混合资料全改成 assistant，会使玩家原输入和程序摘要都像模型的历史输出；全改成 system，则会把有损的生成摘要提高到指令层。历史背景也不能伪装成没有对应调用的原生 tool 结果。当前保留资料的 user role，并明确来源；不同模型/兼容服务对布局的效果仍须实际验证。

本快照中可确认的程序错误是：`26-recap.js` 创建了三种不具名的背景 user，`15-generate.js` 随后给所有 user 默认填写玩家姓名，导致前情提要和玩家/AI混合档案都冠上 `name:'陆清淮'`。内部原文已经标注说话人，但外围姓名造成相互矛盾的身份提示。

## 本次已经修复

1. 三种提要背景增加内部 `_contextOrigin:'story_archive'`，标题标明「程序提供/整理的历史资料，非玩家本轮发言」。保留最近 RP 内的玩家/AI来源标注和微信原发送方向。
2. RP 组装对 story_archive 不再默认填玩家 name；真实玩家历史及本轮输入仍保持姓名。摘要、RP窗口、微信窗口各自保持独立消息。
3. `data-services.js` 的标准化保留来源标记，并阻止不同来源的连续同 role 消息合并；原有 `_preventContextMerge` 保护继续保留。RP API 字段映射仍剔除内部标记。
4. 微信共享同一批背景标题，提交到微信模型链路时仅取 role/content，内部来源与合并标记不发送到 API。
5. 快照还有 6 处未展开的 `{{char}}`，而 `{{user}}` 已展开。`02-state-settings.js` 新增提示词专用 `replacePromptNamePlaceholders`，在 `10-methods-core.js` 的 isPrompt 路径解析双方姓名，system 提前返回前同样完成替换。每次读取当前角色，不缓存旧角色姓名；显示路径沿用原玩家占位符处理。

刷新页面后，新请求使用修复；旧 tmp.txt 快照不会改变。没有改写角色卡、保存的聊天正文或已有提要，也没有本次自动删掉用户预设或世界书。

## 仍存在的指令压力

- 世界书仍要求「甜的三条硬指标（每一到两轮对话至少落一条）」，列举了需要玩家行动的亲密互动。它与运行时“等待玩家决定、允许维持现状”产生张力。建议改成按情境选择的表现方式，不强制频次。
- 卡片里的「他赢了比赛，第一件事是给她发消息：‘赢了。’她回：‘嗯。’」是行为范例。不能因为本轮玩家说完成工作，就推成这次也发送过消息，更不能搬成角色的新来信。卡片来源标题已有帮助，素材中仍宜明确范例用途。
- 四条固定预注入对话中有两条模拟 assistant 分析；它们每轮出现，却不是本次实际剧情。建议在预设中评估关闭或改为清楚标注的范例。
- system、下一轮规则及卡片要求有重叠。继续增加重复禁令可能扩大输入并增加冲突；应先减少重复、统一含义。

本快照没有配对的错误回复，无法证明某条提示是特定幻觉的唯一原因。姓名错标、未解析占位符和重复文风是可核实的组装问题，其余需要真实模型对照验证。

## 建议的下一阶段结构

| 顺序 | 消息用途 | 身份与内容原则 |
| --- | --- | --- |
| 1 | system 规则 | 集中维护角色职责、玩家决定权、知情来源和本轮实际工具；写作规则减少重复 |
| 2 | user 角色/世界资料 | 不冠玩家姓名；设定、例句、未发生的可选情节分别标明；世界书按相关性加载 |
| 3 | user 历史摘要 | 不冠玩家姓名；保留时间、发送方向、否定、未决事项与来源；摘要是有损资料 |
| 4 | 最近真实历史 | 原消息按原 user/assistant 与时间顺序提供；跨渠道档案保留各段说话人 |
| 5 | user 当前玩家输入 | 保留真实玩家姓名；正文清楚呈现当前输入，写作规则集中到 system |
| 按需 | 原生工具调用/结果 | 保留真实 tool-call 配对；原文核实、通信送达依实际执行证据 |

这张表是后续设计建议，尚未对整个管线实施重新排序或大幅精简。调整时还要照顾世界书深度插入、微信时间交错、UI变量纠错、多模态附件、不同提供商及原生工具签名。

以本轮为例，02:00完成工作是玩家明确给出的世界事件；苏祈雪是否知道取决于她是否在场、收到消息或经其他渠道获知。旁白能叙述事件，不会自动向所有人物共享。若后来需要确认具体约定、消息原话或谁已经知情，现有 `tool_search_history/tool_read_history` 可以按需查原文，查不到保持未确认。工具已经通过原生 schema 和 system 说明提供；效果不依赖再写一遍工具名字。

参见 [请求调试与原文检索](./history-retrieval-and-debug.md)。前情提要仍读保存的完整正文，逐轮记忆不会先把磁盘原文改短；增强召回已排除提要覆盖的旧总结。摘要协调不等于能恢复所有压缩细节，核实具体事实时优先看带来源的原记录。

建议真实模型对照检查玩家草稿、玩家明确发送、指定角色发送、分开后的事件是否被无渠道知晓、旧摘要与玩家更正冲突、未知约定是否检索。保持模型及参数一致，记录错误发送/代写/认知泄漏，再比较布局。单纯降低温度或让模型口头自检不能证明归属判断正确。
