# 模型请求调试与压缩后原文检索交接

日期：2026-11-08。沿用原 RP-Hub 的聊天快捷面板、记忆设置与工具等待区域；本工程不按 CWUI 改造。

## 1. 使用入口

- 聊天输入区的「快捷面板」新增 **请求调试（Console）**，默认开启。打开浏览器开发者工具（F12）的 Console，筛选 `[模型请求]`，展开对应请求即可查看 `messages` 对象与带换行的 `messagesJSON`。
- 「记忆系统 → 记忆系统设置」新增 **压缩后按需检索原文**，默认开启。此开关独立于基础/增强记忆模式，也独立于普通主动工具开关。关闭记忆但已有前情提要时，仍可以检索。
- 两个设置沿用全局 `settings` 的保存/加载，不改变角色卡和历史消息格式。

日志在每次实际 HTTP 请求的 `fetch` 前打印，包括 RP 主回复、微信回复、工具续写、逐轮总结、二次压缩、前情提要及其他共用聊天请求入口的副模型。自动重试的每次实际发送也会打印，标题含模型、请求类型与尝试次数。向量请求只有 `input`，没有 `messages`，不在这项 messages 日志里。

日志取实际请求体的 JSON 快照，不保留 Vue 响应式引用；随后编辑聊天不会改变已经打印的内容。工具调用 ID、结果和服务端签名按请求原样保留。日志不打印请求 URL、Authorization 或配置 Key；**消息文本、角色设定和多模态附件本身会原样出现**，它不是聊天内容脱敏功能。Console 的钩子报错不阻断发送。

## 2. 每层总结究竟读什么

| 层级 | 输入来源 | 普通聊天如何使用 | 是否改写保存的原文 |
| --- | --- | --- | --- |
| 逐轮记忆 | 当前目标轮的完整 RP 正文，加最多前三轮原文作背景；去掉 CoT/界面注入，只总结指定目标轮 | 保留楼层之外，用该轮总结替换旧 AI 正文的上下文版本 | 否 |
| 二次记忆压缩 | 逐轮总结，以及保存的玩家原输入用于来源核对；缺原输入时明确未确认 | 合并更早的总结组，保留源总结与原消息引用 | 否 |
| RP/微信前情提要 | 保存的完整 RP 正文与微信记录，按统一时间线交错；已有提要另作一条输入 | 提要代表已覆盖旧内容，另带用户设置的最近 RP/微信原文窗口 | 否 |
| 增强记忆召回 | 对「玩家原输入 + 逐轮总结」建立向量，用本轮玩家输入召回相关总结 | 补充未被提要覆盖的候选概要，需要向量服务 | 否 |
| 本次原文检索 | 当前角色/分支保存的 RP 与微信原文，不搜索生成的总结 | 只把本轮查到的短证据交给模型，下一轮不重放工具结果 | 否 |

因此，开记忆系统后再点「压缩上下文」，提要仍读完整保存的正文，不会拿记忆替换后的聊天上下文作压缩素材。再次压缩也会读取覆盖点以内的完整原文，并另外携带已有提要。目前这样做能重新核对细节，但长历史的提要请求仍可能很大；这次没有改成只压缩新增部分，避免无声地改变现有来源核对规则。

这里的「完整原文」指保存的正文文本，不包括旧 CoT、界面指令、图片字节或文件正文：图片保留画面描述，语音保留文字，文件保留引用。实际像素与文件内容仍由对应资源工具按需读取。

## 3. 两种压缩的协调与修复

两套机制不会把磁盘原文互相覆盖，但摘要都有损，叠加重复摘要也可能让旧解释反复出现。已有提要覆盖范围会排除旧 RP 原文及其逐轮记忆，微信同样只注入未覆盖记忆。

本次补上两个遗漏：

1. **增强召回按覆盖范围过滤。** 已有提要覆盖的旧轮次总结，不再经向量通道重复注入；二次压缩内保存的源总结也按原轮次过滤。若所有有索引的总结都已覆盖，主回复不再为这些旧总结请求向量。未覆盖轮次照常召回，删除提要后恢复原召回范围。另过滤与当前上下文消息内容完全相同的总结；这不是语义去重。
2. **RP/微信先加载提要，再组装请求。** 原来角色/分支 watcher 异步读提要，立即发送时可能尚未加载，导致请求忽略覆盖范围。现在两个渠道先等待本作用域提要，再选择工具并组装消息；等待中停止、清空或切作用域会取消此次请求并清理生成状态/计时器。

摘要不作为精确原话或玩家决定的唯一证据。具体约定、否定、时间和人物是否知情，应优先核对保存的原记录，并服从当前明确更正。

## 4. 原文工具与边界

出现已有提要、开启记忆且已有总结，或保存的微信消息超过 30 条时，才向模型提供这两个内部工具。RP 与微信共用执行器；工具始终可选，不随普通主动工具的「强制调用」策略变成必选。

```json
{"name":"tool_search_history","arguments":{"query":"钥匙 周五","channel":"all"}}
```

`query` 为 2–120 字符，用空格或逗号等分隔最多 8 个具体关键词，按任一词匹配；`channel` 为 `all/rp/wechat`。在完整保存正文中扫描，长正文尾部也能命中。英文 ASCII 大小写不敏感，其他 Unicode 字符按字面匹配，保持 UTF-16 字符位置正确。返回最多 3 个命中，包含来源、消息 ID、RP 轮次或微信时间、匹配片段和字符范围。

```json
{"name":"tool_read_history","arguments":{"recordId":"rp:消息ID","startChar":200,"length":1600}}
```

只能读取**本轮成功搜索返回**的 ID，按字符位置读取最多 1800 字符。搜索后原文被编辑/删除，或 ID 未被本轮授予，拒绝读取并要求重新搜索。

每轮最多 4 次搜索/读取，结果总预算为序列化 JSON 的 12000 字符，包含来源与核实规则；重复相同调用拒绝。RP 沿用原生工具续写，微信沿用现有顺序工具循环（有原文工具时最多 8 次模型请求，原文执行仍受四调用限制）。工具循环会增加聊天模型的请求次数和输入量，检索本身在本地运行，不调用向量或网络搜索。

原文来源与清理规则：

- RP 镜像只用来确定交错顺序，不作为另一份重复记录。玩家输入和 AI 叙述分别标记；旁白不能单独证明玩家已选择、发送或已读。
- 微信文本、语音文字、表情名称、图片描述和文件引用可搜索；实际图片字节与文件正文不在此搜索中。
- 预算记录角色 UUID、分支 scope、会话 revision 和媒体 epoch。作用域切换、清空或停止后，旧结果和读取授权作废。
- 每次执行都确认当前分支的微信时间线已载入，即使该角色后来关闭微信开关。读取失败报错，不把旧作用域内存当作当前历史。
- 没有持久化搜索索引或跨轮结果缓存；切分支/清空时释放临时原文授权。检索结果不保存为角色发言、剧情正文或记忆来源。RP 工具折叠区沿用现有调用记录，会保存检查用的 `resultText`，但它不参与下一轮上下文或原文搜索；微信工具结果不进入气泡记录。清空全部 RP 时这些 RP 调用记录随消息一起移除。

关键词检索会漏掉同义词、代词和不含关键词的相关事件，模型也可能不调用工具。可以换具体人名、物件、地点或原话再查；仍查不到只表示「无法核实」，不表示「从未发生」。即使取回 AI 原文，也只能证明那段旁白写过，不能自动认定人物知情或玩家授权。本能力帮助找依据，不保证消除幻觉。
