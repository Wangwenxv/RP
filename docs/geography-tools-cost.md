# 地理工具组合查询、并行调用与上下文预算

2026-11-06后续优化。承接[江大南校区地理试点](./geography-pilot.md)。用户确认本项目不属于CWUI，本次保持既有Vue、页面与微信风格，没有新增组件或改动样式。

## 用户问题与原实现的准确情况

用户希望“我在风采园，你在哪里？”能一次取得风采园的位置、用途/介绍及双方路程，避免拆成多个模型请求增加费用。

原来的业务层已经可以处理一个响应中的多个`tool_calls`：RP用Promise.all执行后集中回传；微信遍历全部调用后才续写一次。因此，本地执行三个工具并不天然等于请求三次模型。

但共用API层此前写死了`parallel_tool_calls: false`，模型通常只选一个调用再等待。这是限制多调用的真正挂点。本次RP和微信请求都主动启用`parallelTools: true`，API层传递`parallel_tool_calls: true`，允许模型同一次返回多个业务工具调用。

例外：当RP的`output_reply`回复工具也在本轮工具表中时，API层继续关闭并行，避免现有解码器把正文输出工具与业务工具混用。强制业务阶段没有提供`output_reply`时可以并行。组合查询`context/batch`在单工具模式下仍然有效；不能宣称所有输出模式一律开启并行。

## 费用与请求次数

地图解析、地点查询、介绍读取和路线计算全部在本地执行，不会额外调用识图或读者模型。正常模型API的主要消耗仍是每次请求的输入、输出和提供商计费规则。

| 一次地理问题的处理方式 | 常见模型请求次数 | 地图计算 |
| --- | --- | --- |
| 分别查地点→介绍→路程，每次等结果再决定下一步 | 4次：3次工具决策＋最后回复 | 本地 |
| 同次返回3个独立工具调用，收齐结果后续写 | 2次：一次工具决策＋一次回复 | 本地 |
| 一次`context`或`batch`组合查询 | 2次：一次工具决策＋一次回复 | 本地 |
| 本轮问题触发自动短速查，模型直接回答 | 1次：直接回复 | 本地，无额外模型请求 |

这不是费用百分比承诺。真实模型可能补查，地点歧义也可能需要澄清；上下文大小、输出长度、模型和提供商价格不同。测试验证的是上述请求链能够成立，不能保证任意模型每次都选择最省的路径。

## 推荐调用方式

一次查齐地点用途、环境、位置证据、步行和骑车：

```json
{"operation":"context","query":"风采园"}
```

它默认从`character`最近确认位置到`query`地点；省略query/to时目的地是`user`最近确认位置。**不是先取坐标、再让模型自己算距离**：坐标留在本地道路引擎里，结果直接给可用于决策的分钟数。

需要明确起终点、剧情时间或天气：

```json
{"operation":"context","from":"实验楼A区","to":"风采园","weather":"rain","time":"18:10"}
```

默认返回两种交通方式；`mode: walk/bike`可以只取一种，`mode: compare`显式表示两种。`route`只接受walk/bike，比较时用context。

一次取得多个独立需求：

```json
{
  "operation":"batch",
  "requests":[
    {"operation":"place","query":"风采园"},
    {"operation":"status"},
    {"operation":"route","from":"实验楼A区","to":"风采园","mode":"walk"}
  ]
}
```

每次batch最多4个查询，不能嵌套batch。每个结果带index和自己的status；未知地点仍保留需澄清的结果，不能把它当成查询成功。

确实需要丰富背景或坐标时才取full：

```json
{"operation":"place","query":"风采园","detail":"full"}
```

此时返回区域背景和归一化图片坐标。默认brief省略原始坐标、完整区域世界书和长路线节点列表；保留地点名、用途、短场景、开放约束和估算分钟。

## 自动准备的本轮速查

RP和微信共用`buildGeographyPrompt`。最新用户文字明确提到绑定世界中的地点，或询问在哪/路程/见面/接送时，本地准备短context后再发主模型请求。模型无需为已有资料再查三遍。

例如用户已明确在风采园、角色最近明确在实验楼A区，本轮短资料包括：

- 用户与角色最近确认的位置及来源；工具知道不等于角色全知。
- 风采园是南苑西南角、靠近13栋的校内食堂，用途、短介绍、用餐时段。
- 两边沿可走道路的步行/骑车耗时区间和限制。

用户只说“风采园”不会自动改写user位置；提及地点不是位置事件。若没有角色当前位置证据，返回needs_location，不能因为住3栋就假定此刻在3栋。若问题有多个明确起终点，自动速查按最近位置和最长名称提及准备，模型仍需要核对实际需求并调用明确起终点的context，不能将预取当成万能意图解析器。

普通“谢谢啦”没有地点或地理问题时，不再附上区域介绍和路线速查；最近位置证据与短工具规则仍可以存在，供后续场景连续性使用。

## 上下文隔离与预算

不能做到零token：工具schema、短规则、最近位置和实际需要的事实仍会占上下文。本次减少的是整张地图、完整区域介绍、重复查询和跨轮工具重放。

- `brief`只带短地点用途/环境和行动事实；角色自己的地点记忆默认最多140字符，full最多600字符。
- 单条brief结果或batch合计预算6000字符，full最多12000字符。超过时移除场景长文、区域长文、长节点列表等可选字段，保留路线时间、开放限制与状态；仍过大则明确返回result_too_large，不剪断JSON假装完整。
- RP和微信每轮最多4次地理工具调用；batch内最多4项。每轮成功地理资料合计最多12000字符，达到预算后要求依据已有结果回答。
- 同轮相同查询按规范化参数、世界、scope和位置证据去重，返回already_returned及原callId引用，不再次返回整份资料。它能防止重复结果膨胀，但如果模型已经再次调用，仍可能需要一次API续写；提示词优先要求模型避免重复调用。
- 本轮工具结果保留正常调用ID配对和必要签名，不能为了压缩随意删除未完成的tool消息。
- 微信工具结果不写入气泡或微信时间线；RP工具详情沿用原审计展示，可在本地消息对象中保存，但不会作为native tool消息注入下一轮正常聊天。
- 最终角色自然说出的路程/情节属于正常对话，照常进入剧情与记忆；不应为了“清理工具”把角色真正说过的话删掉。
- 新轮次重新准备当前需要的数据，不重放旧native工具消息。位置依旧从真实历史重放，编辑、删除、换分支规则保持原试点口径。

## 并行与依赖关系

RP已经并行执行同次多个业务调用，本次补齐API开关。微信将同次独立地理读取集中计算，再按原调用顺序回传，与其它工具共用一次续写。

微信的文档读者、图片加载等管线继续按原顺序执行，保持共享字符预算、阅读进度和资源副作用的约定；即使本地顺序执行，**同一响应的一组工具仍只触发一次模型续写**。

存在真实依赖时不能硬并行。例如先查未知附件ID再读附件、先拿新地点候选再确定唯一目的地，需要模型或用户先解决依赖。地图context/batch的好处是将可在本地解决的地点解析和路程依赖一起完成。
