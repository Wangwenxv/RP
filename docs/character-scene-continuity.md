# 单卡 RP / 微信场景连续性（2026-11-20）

以江拾卡、`tmp/duihua.txt` 和门诊部门口微信对话复现。修改的是共享运行时，未给某一张卡添加特殊分支。

## 问题与处理

- RP 的位置工具在调用时绑定正文。工具续写会继续追加到同一个气泡，原有工具队列在最外层结束后才重新绑定正文；中途下一次请求可能把位置判成已编辑失效。现在每段程序续写完成、进入下一次工具处理之前就更新绑定。用户手工编辑仍按原有证据规则重放。
- RP 场景提示混入微信 JSON 规则，又鼓励停留与室内描述反复提交位置。两渠道现在分别说明格式：RP 原地继承，地图仅按需查询/实际移动登记；微信普通原地回复可省略 `position`。`detail` 为可选描述，不再因为缺少楼内细节阻断消息；重复原地描述保留原来的到达时刻。
- 已明确写出的双方具名位置、以及已知建筑后的门口/诊室/走廊等描述自动回放。玩家自己写出的角色位置归角色，玩家姓名或第一人称的明确位置归玩家。计划、问题、引文仍不定位；模型的自身工具不代玩家决定去向。
- 角色卡开场具有当前时间、全文只有一个明确地图建筑、具名人物确实出现在现场时，可从开场建立双方位置。来源是已写好的开场，不是住址或模型新替玩家做的行动；多场景或模糊地点仍不代填。已有建筑内的“门口”“房间”等相对描述保留该建筑，只细化室内位置。
- 微信时间以前只解析首行完整公历格式。现在也以分支日历解析首行中文时间、中文月份和相对第 N 日；未给年份时继承参考年，不使用现实日期。月末/月底用当月最后一天作日历占位，月初/上旬/中旬/下旬分别用 1/5/15/25 日。无任何时间线的新分支仍保留旧默认日历兜底；江拾开场会得到参考年 11 月 30 日 16:15。后续只写“16时”不会把 16:15 倒退为 16:00。首次 RP 工具执行即能读到开场时间，不必等打开微信镜像。
- 已建立的剧情钟也注入 RP 请求。实际推进时间时要求在正文首行使用完整公历时标，避免只在正文中间写时间、微信却仍沿用旧时刻。
- 玩家明确指定当前角色发消息时，原生 API `tool_choice` 指定微信工具；计划、玩家草稿、商家/其他收件人和疑问不强制。还兼容模型漏掉原生工具、只在 RP 正文写出明确发送动作和完整引号消息的情况：核对最近具名角色、微信渠道及收件人，取第一条实际原话执行现有交接流程，截去随后自行补演的消息/回复。此路径标记 `origin: narrative_handoff`，不冒充模型的原生调用，也不额外请求模型。
