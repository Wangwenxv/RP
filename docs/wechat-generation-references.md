# 微信图片按需用于生图与模型跟随

更新：2026-11-25。当前单卡微信可以把本会话已发送的图片按用途交给生图模型，保持原有Vue/UI、图片气泡与工具协议。

## 2026-11-25：取消关键词门槛，每轮直接提供生图格式

用户指出隐含语义不可能靠穷举关键词覆盖，要求模型在需要图片时自主生图。现在删除 SEND_ENTRY 及接受照片邀请的固定短语匹配，resolveWechatMediaContext 只收集图片状态，不判断是否发图。每轮系统提示直接提供当前服务的 generate 格式、场景要求、selfPortrait 与 generationReferences 用法；无需先调用工具取得生图资格。是否发送由主模型结合当前语义、前文承诺、人设意愿和通信处境决定，原有拒绝、推迟和空回继续有效。

tool_load_image_sending 每轮保留，用于按需取得相册素材、绘图/搜索详细格式及近期48条记录的微信图片目录；明确请求、暗示和普通聊天均不自动查询相册。聊天中保留的 [图片 #ID] 可以直接作为 generationReferences 来源，细节不清楚时查看旧图；查目录和查看像素都不等于选中生成参考。本人入镜仍自动附当前卡人物参考，衣服等聊天图仍须明确指定用途。

这项变化每轮增加固定的生图文字说明与角色参考目录文字；不会在普通文字轮自动读取或附上角色/历史图片像素、自动付费生成或增加一次分类模型请求。素材目录、已查看图片与独立比对结果仍为本轮临时资料，下轮卸载；生图格式本身保持可用。

新增fixture回放覆盖“好了吗？”“让我过过眼瘾”“想看看你现在什么样”“这一身一定很适合你”：主模型首个最终JSON直接提交generate，程序一次生成取得人物参考3张＋旧衣服参考1张，零素材查询、零工具续写。另验证照片关键词、暗示和普通聊天得到相同能力格式，接受邀请也不自动查相册；按需目录和原有失败/取消/场景修正链路继续验证。fixture只证明格式可用与执行路径，不证明真实模型理解所有暗示或每次都输出正确意图。

## 历史诊断：照片承诺后只说“发了”，没有进入生图

用户提供 request-1795576817459-14 的模型原文：玩家此前发过衣服图、请求试穿照片；角色答应去水房换衣，下一轮玩家问“好了吗？”。qwen3.7-plus 最终只返回三个 text（“发了”“水房好冷 冻死我了”“好看吗”），没有 tool_calls 或 image_request。这份响应能证明没有产生图片决策，不能据此确认参考图或衣服像素已进入生图请求，也不能归因为生图接口失败。

当时发图能力匹配仅扫描尚未处理的玩家文字；“好了吗？”不含发图关键词，上一轮的照片请求已处理、上一轮角色又没有明确的照片邀请，故本轮保留简短 tool_load_image_sending 入口。旧入口强调“可选、不必调用”，却没有说明跨轮照片承诺同样适用，也没有约束只用文字冒充发图。原文显示模型沿着这一入口选择了纯文本，误以为本轮没新图或没相册就无需加载。

第一次修改先补强轻量入口、加载工具说明和完整能力说明：结合前文判断是否兑现照片承诺；愿意现在发送且缺格式时，先原生调用 tool_load_image_sending，再在最终 messages 中输出 image_request，不能只以“发了”“拍好了”“好看吗”或“[图片]”代替图片。用户随后指出关键词门槛的问题，现由上面的每轮直接格式取代该加载前置条件；图片实际发送与参考用途规则继续保留。

保留原有按需工具和 tool_choice:auto，没有新增关键词强制生图、逐轮相册/参考像素加载、台词关键字拦截、付费重试或人格修改。角色仍可推迟、拒绝、空回；已发送旧图的回忆不用重新生成。纯文字本身仍不会触发生图，提示改进不等于程序能够识别并拦住所有自然语言里的虚假发图声明。

新增离线回放使用“旧衣服图＋拍照请求＋去水房换/你等我＋好了吗？”，验证首请求保持轻量入口和零图片附件，一次加载取得真实旧图 ID 后，生成收到人物参考3张＋clothing参考1张；消息顺序为文字/真实图片/文字/文字，相册为空仍可生成。另覆盖轻量与完整说明下的拒绝、旧图回忆和空回，不发生自动生成。资料与选图字段不落时间线，普通下一轮卸载；使用 fixture 模型回复，不是 qwen3.7-plus 自主工具选择的实测，不能据此宣称真实触发率或最终画面已验证。

## 使用方式

玩家上传衣服后说“穿这件给我看看”，模型可以在愿意发图时选择这张图片作为clothing参考；上传地点图说“在这里拍”，可选择background参考。本人入镜时仍自动带当前角色的人物参考。只拍宿舍、风景、饭菜或物品时填selfPortrait:false，不附人物参考；背景参考也按实际需要选择，没有参考时仍是普通文生图。

tool_view_image负责按消息ID查看真实画面。新图已经在当前视觉请求中，旧图需要核对未保留的细节时才调用查看工具。模型决定生图时，把需要的图写入最终image_request.media.generationReferences；看过图片不自动选中它，也不自动把全部历史图片发给生图服务。生成格式每轮直接提供；tool_load_image_sending仅按需补充素材详细说明、近期48条记录中的图片目录与可用来源，更早图片仍可以按当前会话里的完整真实消息ID选择。

```json
{"type":"image_request","media":{"mode":"generate","selfPortrait":true,"prompt":"穿参考图中的连衣裙，在参考宿舍中拍一张自然自拍。","description":"宿舍里的新衣自拍","generationReferences":[{"messageId":"衣服图片消息ID","purpose":"clothing"},{"messageId":"宿舍图片消息ID","purpose":"background"}]}}
```

| purpose | 继承范围 |
| --- | --- |
| clothing | 服装款式、剪裁、颜色、图案和材质，优先于人物身份图里的旧服装 |
| background | 背景布局、环境，图中的陌生人不变成当前角色 |
| pose | 动作、姿势，仍服从本轮机位与手部占用 |
| style | 画面视觉风格 |
| object | 本轮需要的物品 |

聊天参考不能指定identity；角色稳定外貌继续来自当前卡的身份参考。每张聊天图指定一个用途，相同ID与用途去重，不允许同一ID给出互相不明确的不同用途。消息ID允许一个前导#，按当前微信时间线查找。不存在、属于其他会话、只有画面描述、资源丢失或取消的图片不能冒充已经送入生成模型。

## 传输与保存

程序先校验整批ID与总数量，再读取完整像素。人物、已选择的卡内地点图和聊天参考合计最多16张；既有单图6MB、参考总24MB与实际图片签名检查保持。支持参考图的OpenAI Images服务继续按配置使用image_data_urls、image_urls或multipart，Chat生图继续使用多模态content；NAI和未启用参考图输入的协议在付费前报错，不悄悄丢掉所选参考。

本轮主请求、查看工具与生成共用临时像素缓存，已读的聊天图和角色参考可复用。临时聊天参考带generationPurpose供生成提示标注用途，不加入角色卡。生成模型收到有顺序的全部选中像素和对应用途；服装、背景等参考不迁移其他人的身份或经历。

媒体任务只保存选图消息ID、用途与原生成计划，像素仍在媒体库。刷新或手动重试时按同一会话重新取得选中的资源；成功生成的资源检查点沿用原逻辑，不重复付费生成。图片气泡和后续对话不保存generationReferences、临时参考像素或generationPurpose。生成描述仍标注为来自生成计划，不冒充已核实的像素细节。

## 微信识图模型跟随

用户截图里的temperature:0.1、stream:false请求属于前置画面观察，而不是角色主回复。旧实现优先读取settings.visionModel，因此即使RP输入框切换settings.model，识图仍可能使用此前配置的qwen3.7-plus。

新增settings.wechatVisionFollowsChat，默认true，旧设置缺少该字段时同样跟随。设置页面“识图模型”下有“微信识图跟随当前聊天模型”复选框：勾选时，微信人物比对、历史图查看与主回复采用当前聊天模型；取消勾选时，识图使用单独的visionModel，主回复仍使用当前聊天模型。RP原有单独识图配置不清空。

一次微信回合开始时固定本轮主模型与识图模型，工具续写使用同一快照；回合中切模型不会让半轮请求混用，下一个回合采用新选择。画面处理状态显示实际识图模型，请求摘要保留原来的请求标签与model字段。
