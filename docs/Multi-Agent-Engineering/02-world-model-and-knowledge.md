# 世界模型、事件与角色认知

> 本文保留原方案的数据设计。哪些契约已经实现、哪些仍待扩展，以 [06 实现交接](./06-implementation-status.md) 为准。

状态：提议的数据契约，当前工程尚未实现。日期：2026-11-11。

## 1. 六个概念必须分开

| 对象 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| CharacterCard | 可复用、版本化的人物定义与原文条目 | 不是某次存档中的全部人生历史 |
| WorldDefinition | 江南大学的公共设定、地图引用、人物名册与关系绑定 | 不是“所有人物都知道”的资料包 |
| WorldSession | 玩家启动的一份世界存档，固定玩家身份与规则版本 | 不是某一张卡自己的私有聊天 |
| WorldBranch | 该存档的一条时间线，包含全部人物与会话 | 不能分别给苏祈雪和卿回到两个互相矛盾的时刻 |
| Conversation | 私聊、群聊或 RP 场景，具有参与者与访问规则 | 不用 user/assistant 推断世界里的发言者 |
| Event / ActorKnowledge | 已发生事件及某个角色如何获知、相信或怀疑某个命题 | 模型提案、旁白展示、消息内容都不自动成为客观真值 |

建议引用关系：

```text
WorldDefinition(worldId, revision)
  ├─ actors: actorId -> cardId + cardRevision + relationshipBindings
  ├─ geographyRefs: mapId + mapRevision
  └─ WorldSession(sessionId, playerActorId)
       └─ WorldBranch(branchId, parentBranchId?, forkAtSeq?)
            ├─ events / branchHead / storyClock
            ├─ conversations / membership / readCursors
            ├─ actorState / actorKnowledge / pendingActions
            └─ RP正文、微信气泡、摘要等派生视图
```

`actorId` 是世界中的稳定身份，显示名和别名可变。相同卡在不同存档中的记忆不互通。卡的同名、同头像、相同院系都不能作为合并身份的证据。

示例名册：`player`、`suqixue`、`linwan`、`qing`。实际持久化使用稳定 ID；示例字符串仅用于说明。卿明确为 NPC，林晚卡中的恋人槽位绑定卿，不能把 `{{user}}` 全文替换成玩家。旧占位符须在导入适配时区分“扮演接口中的玩家”和“人物设定中的恋人”。未能解析的槽位保留冲突，不静默猜测。

## 2. 卡牌不是整段公共知识

保留原始卡及哈希，生成可审阅的编译版本：

| 层 | 示例 | 使用者 |
| --- | --- | --- |
| 人格内核 | 价值取向、说话方式、边界、稳定动机 | 本角色模拟器，每轮必需 |
| 个人背景 | 经历、本人掌握的技能、自己的秘密 | 本角色，或具有获知来源的他人 |
| 可观察资料 | 外观、公开身份、已介绍过的姓名 | 满足认识/观察条件的人物 |
| 世界硬设定 | 地点名称、路网、世界年代 | 世界运行时；人物按熟悉程度获得必要内容 |
| 关系事实 | 林晚与卿的恋爱关系 | 先存世界关系；是否公开另行标记 |
| 主观关系 | 林晚信任谁、苏祈雪如何理解林晚 | 关系有方向，属于持有者视角 |
| 风格范例 | 示例聊天、假设约会片段 | 只作风格资料，不能检索成发生过的往事 |
| 情境条目 | 某类冲突时的反应倾向 | 按相关性取回原文，仍受玩家边界约束 |

导入产物至少保留 `sourceCardHash/sourcePath/entryId/version/contentKind/visibility`。低置信度自动分类需要可复核；不能先自动摘要删除原文，再把摘要当无损替代。

当前世界以苏祈雪 v2 为基线。林晚独立卡中毕业、同居、不同年级/校区等内容不能直接并入；用户将准备适配卡。保留冲突报告即可，本次不替用户改人设。后来升级卡也应显式生成新版本，旧分支固定旧版本；修订世界设定需要迁移或新分支，不悄悄改写过去。

## 3. 事件记录什么

一个事件尽量只有一种信息范围。把公共气泡与隐藏动机拆为两个事件，避免“读取气泡时顺便读到私心”。下列为逻辑结构，不是已发布的 JSON Schema。

```json
{
  "eventId": "e-204",
  "sessionId": "s-1",
  "branchId": "main",
  "seq": 204,
  "turnId": "t-18",
  "kind": "message.sent",
  "actorId": "qing",
  "conversationId": "dm-player-qing",
  "storyTime": { "day": "2026-05-12", "minute": 1061, "order": 0 },
  "recordedAt": "2026-11-11T08:00:00Z",
  "causedBy": ["e-201"],
  "source": { "kind": "npc_generated", "runId": "run-q-18" },
  "access": { "principals": ["player", "qing"] },
  "payload": { "text": "ok", "inReplyTo": "e-201" },
  "idempotencyKey": "t-18:qing:reply:0"
}
```

示例剧情日期是虚构测试数据，不是从角色卡推定的当前剧情时间。`recordedAt` 用于操作审计，不能驱动剧情。`seq` 是分支内提交顺序；`storyTime` 是虚构世界时间。群聊同一分钟内可以用 `order` 排序，不必给每个气泡硬推进一分钟。

建议的第一批事件类型：

- `player.input`：原始玩家输入及明确标记的渠道/输入模式。
- `message.sent`、`message.delivered`、`message.read`：通信与阅读，读者、范围和原消息可定位。
- `action.committed`：经过批准、条件满足且实际完成的动作；尚未完成的行为留在任务表。
- `observation.acquired`：谁通过在场、阅读、告知或其他渠道获得哪些信息。
- `world.fact_asserted` / `world.fact_corrected`：作者明确设定或经裁定生效的世界事实，带来源和被更正对象。
- `narration.published`：展示给玩家读者的正文及覆盖的事件 ID，不自动授予角色知识。

这些类型可以按里程碑增补，第一版不需要给每一次眨眼都记账。对白、承诺变化、保密/告知、位置变化、关键行动与知识传播需要结构化；无后果的修辞可以只留在正文。

## 4. “说过”与“是真的”

玩家对苏祈雪说“今晚与卿打球”，能确认的是这句话已发出，不是今晚一定打球。玩家随后对卿说“取消，准备惊喜”，也首先是一条发言；若是明确取消两人的安排，可以创建取消约定的事件。准备礼物的动机可以在玩家明确剧情前提中成为事实，或在私聊中作为玩家声称的动机存在。

因此至少区分：

```text
Event: player 对 qing 发出了“取消打球”
Claim: player 声称今晚准备礼物（reported，不自动证真）
Commitment: player-qing 今晚打球安排已取消（有双方对话来源）
Belief(qing): 接受取消；相信玩家在准备惊喜
Belief(suqixue): 仍相信玩家去打球（来源是之前的私聊）
```

不同角色的信念冲突可以同时成立。不能用世界的“最新摘要”把苏祈雪原有认知覆盖。角色是否撒谎、是否相信来信，属于与客观事实分离的判断。

## 5. 访问、观察与信念是三层

`access` 表示角色有资格访问该资料，例如属于私聊接收者或在发送时属于群成员；它不表示已经看过。`observation` 表示通过何种渠道、在什么剧情时间接触到具体内容。`belief` 表示对该内容的理解和相信程度。

知识记录建议：

```json
{
  "actorId": "suqixue",
  "proposition": "玩家今晚与卿打球",
  "stance": "believes",
  "sourceEventIds": ["e-100", "e-101-read"],
  "learnedVia": "dm_read",
  "learnedAtSeq": 101,
  "validFromStoryTime": { "day": "2026-05-12", "minute": 1000 },
  "supersedes": [],
  "evidenceStatus": "reported"
}
```

`stance` 可取 `knows_source_exists/believes/suspects/disbelieves/unknown` 等少量值，不需要伪精确到 0.873。核心是区分确定来源、角色推断和未确认。记录“她听林晚这么说过”比无来源地记录“她知道事实”更可靠。

私密信息转述可以合法传播，但要创建新的通信/观察事件，保留原来源链。原私聊本身不会因此向新人物开放。转述可以遗漏或说错；不能自动把原文完整复制到接收者记忆。

玩家读者是单独的展示主体。NPC 镜头可以展示林晚与苏祈雪的秘密对话，但 `playerActorId` 没有亲历或接收事件，就没有相应知识。读取调试面板同理。

## 6. 群聊阅读的最小可落地规则

每个群成员保存成员资格的生效区间和 `lastReadSeq`。新成员默认不获得入群前历史；未来若开放历史，必须有显式规则。退出、转发、重新入群也不能只依据当前成员列表判断旧消息权限。

第一版采用以下简化，保持语义一致：

1. 玩家发送时提交消息，按发送时成员名单确定可送达范围。
2. 调度器依据已知状态选出可以查看手机的 NPC，为其提交本批次的阅读观察。此处允许“看了但不回”。
3. 该 NPC 的上下文只包含已经取得阅读观察的消息。角色模型可以回复、稍后回复或沉默。
4. 没有查看手机的人保留未读；后续玩家操作推进到合适状态时，才获得历史阅读观察并更新上下文。
5. 玩家角色的已读不由 NPC 模型补造。打开对应会话等明确交互才可以按产品规则记阅读；读者看了 NPC 镜头不算玩家读过微信。

通知预览可以之后补成部分观察；第一版不必模拟锁屏逐行显示。未读消息可保存在会话中，但角色回忆工具默认不能通过直接读取原文绕过阅读状态。若支持主动查看消息，应通过有记录的 `observeConversation` 动作取得知识，再继续生成。

## 7. 地理、时间与可用性

地图拓扑仍由现有地理引擎负责。世界分支新增 `actorId -> position/activity/phoneAccess/attention/availability`，每项保存来源、更新时间及未知状态。

- 位置：在何处、到达还是计划前往；不是从“图书馆怎么走”推断已经到了图书馆。
- 活动：上课、休息、训练；必须有剧情依据或已批准的日程。
- 手机条件：可用、收起、没电等硬限制。
- 注意力与习惯：可能影响回复时机；人格倾向不能覆盖明确硬限制。
- 行程：出发、路线与耗时、预计到达。长时间跳跃后没有依据的位置保持未知，不自动到场。

剧情时间全分支共享。在玩家本轮只发一句问候时，不能为了一名 NPC 有空而把全世界推进两小时。未来到期动作放入任务表，在玩家明确推进到相应剧情时间后结算。现实播放气泡的动画延迟不修改剧情时间。

## 8. 存储与一致性

继续使用当前 `RPHubDB/store`，先增加独立版本化命名空间，无须第一步迁移数据库引擎。建议逻辑记录为 `world_definition`、`world_session`、`world_branch_head`、分段 `world_events`、`world_projection`、`world_turn` 和资源引用。实际 key 用规范化元组编码，避免直接拼显示名或复用 `getStoryBranchOwnerId()` 去解析新身份。

提交入口概念为：

```text
commitEvents(scope, expectedRevision, turnId, idempotencyKey, events, pendingDelta)
```

在**同一个 IndexedDB readwrite 事务内**读取并比较分支 revision、检查幂等键、分配 seq、写事件/必要投影/任务/新 head。模型请求在事务外执行；不能在 IDB 事务内等待网络。JS 内存锁只能约束一个页面，多标签一致性最终靠事务内比较；可再用 BroadcastChannel 通知失效。

建议单世界分支串行提交，允许不同会话排队；子模型不能直接写库。显示已发送的气泡必须有已成功落盘的事件。投影可重建，但“最新事件已提交、投影仍旧”的状态须由 revision 检查识别，读取时补投影或回退重放，不能悄悄使用旧知识。

历史事件可按块存储并建立快照，避免每次重写整段世界史。快照是加速缓存，必须带 `throughSeq/projectionVersion/cardRevision/mapRevision`，不是新的事实来源。

必须区分两种“重建”：成员资格、阅读游标、已接受的位置变化等从事件确定性重放；模型生成的摘要、信念不是纯函数投影。摘要保存来源范围、生成配置版本和内容哈希，可作为有损缓存，但不能凭重新摘要改变观察授权。会影响后续行为的信念选择应保存为私有的 `belief.adopted` 事件或不可变接受产物，回档时恢复原结果，不重新请求模型猜一次。显式重新压缩产生新摘要版本，不能冒充对旧运行的精确重放。第一版可以只有来源化观察，暂不独立持久化复杂信念。

## 9. 分支、编辑与删除

分支复制整个世界的事件前缀/状态快照，包括 NPC 知识、群成员、未读、约定、位置和待执行任务。初版可以深拷贝一份完整世界快照，后续再优化为事件前缀共享；附件原件可复用引用，回收要统计所有分支。

默认处理原则：

- 只改展示的错字：可以产生正文修订，不改变事件语义；若改变了“去/不去”等内容，则不是单纯错字。
- 更改历史语义、重生成过去回复：从变更点前建立新世界分支，并重新生成后续；原分支保留。不要保留已经失去因果依据的后续泄密或知识。
- 删除气泡显示：与“从世界中撤销该事件”分开。前者不使角色失忆。
- 撤销世界事件/回档：明确回到世界分支检查点，取消之后任务并重建全部角色投影。
- 撤回消息：本身是一件新事件；已读的人不会因此自动忘记。

第一版可以只实现世界检查点回档与重新分支，不必立即实现精细的因果图局部修补。旧单卡模式的编辑/清空入口保留原语义；世界模式不得直接调用它们删除单个角色 scope 来假装完成世界回档。
