# 微信生图格式修正与场景实测

日期：2026-11-13。用户截图是原单卡微信：角色已经决定分享自拍，但最后落成了“画面描述”卡片。测试场景来自本目录 `test文本/2.txt`，测试密钥由用户提供，未写入代码或本文。

## 已确认的缺口

原单卡提示词先给出相册、绘图和完整 `describe` 示例，最后才补充生图示例。配置好生图后 `describe` 仍是可用来源，模型选择它即可直接落为无像素图片，不会调用 API。旧描述图片还会进入后续上下文。RP 主动微信的图片 schema 更明确写着“复杂画面或没有匹配素材时用 describe”，与已配置生图时优先生成的文案冲突。

这解释了模型为何能绕开生图。并非所有回复都会失败：用户打开的线上页面里，角色连续拒绝自拍，随后同意拍校园景色，成功调用 STA1N 并显示了真实图片。因此不能把角色拒绝、描述图片和服务失败当成同一种问题，也不能断言用户 API 配置有误。

## 修改与边界

- `27-wechat-media.js`：使用统一能力判定。全局配置就绪且角色允许时，发送提示先提供 `generate`，不再提供 `describe` 示例。描述模式的新请求会被执行守卫拒绝；相册/绘图失败也不以描述卡片掩盖。无 Key、全局关闭或角色关闭时仍保留旧描述能力。
- `25-wechat.js`：模型最终 JSON 中出现不允许的描述请求时，整批气泡尚未发送，也未付费生图；在原有有界工具循环中追加一次格式纠正。要求保持角色当前场景、补英文画面提示和中文说明，仍允许按人设拒绝或沉默。重复误用则失败，保留待回复消息。主动 RP 图片也执行相同守卫。
- `14-tools-runtime.js`：主动图片说明与 `mode` 枚举跟随实际配置；可生图时枚举为 `album/draw/generate`，未配置时为 `album/draw/describe`。

不按玩家“拍照”关键词强制角色答应，不把模型给出的描述直接拼成提示词付费调用，不自动重试失败的生图 API。格式纠正可能多一次聊天调用；一张正常图片仍只调用一次生图服务。已保存的旧描述图片、旧任务和历史记录不进行自动生图迁移。

## 测试入口与证据

新增 `tools/refactor/smoke-wechat-photo-flow.cjs`，默认隔离 Edge、Vue、IndexedDB 和 fixture API，真实使用微信输入框完成三次连发，再发“我不信”“现在立刻拍张照给我!”。fixture 故意先返回 `describe`，验证一次纠正、真实像素存储、消息时序以及刷新不再生图。图片仅是测试素材，不能当真实视觉验收。

`--live --config <本地JSON> --card <角色JSON>` 使用真实聊天和生图服务，最多八次聊天、两次生图；配置结构见脚本注释。`--scene-followup` 仅在角色未发送自拍且该轮成功时，追加一次“拍眼前景色”的请求。报告分开记录原拍照请求是否发图，不能用补充场景掩盖原轮拒绝。没有图片时报告角色决策，不强制生图。

测试产物位于忽略目录 `.refactor-tmp/wechat-photo-flow/`；报告不包含 API Key，运行时复制的临时密钥配置在验证后删除。独立角色卡实测使用用户的 `qwen3.7-plus`、`https://vsllm.cc/v1` 和默认 STA1N NAI 模型，二次聊天、一张生成图片，持久化后图片为 63,182 字节；刷新仍可显示，没有重复生图，七项断言通过。该次未勾选世界书和预设。

随后复制线上同一苏祈雪 v2 的 **15 条世界书、9 条预设选择** 再实测：18:00/18:05/18:10 连发后，角色回复“在呢 / 刚下课 / 怎么了呀”；收到“我不信 / 现在立刻拍张照给我!”后回复“手都冻僵了还要给你拍照”，直接提交生图并发送自拍，再说“信了吧”。无需补充景色请求。聊天请求 **2 次**，生图请求 **1 次**；STA1N 返回 HTTP 200，下载 PNG **1,671,622 字节**，保存后的图片 **119,808 字节**，刷新仍可显示，七项断言通过。截图为 `live-chat.png`，报告为 `live-report.json`。这是一次成功实测，不承诺模型每次都愿意拍照。
