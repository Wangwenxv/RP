# 实施路线、迁移与后续交接

> 本文保留实施前路线建议。当前阶段、实际文件、数据生命周期与剩余 P4 工作，以 [06 实现交接](./06-implementation-status.md) 为准。

状态：设计建议，未实施。所有阶段以验收条件推进，不给未经开发验证的完成天数承诺。

## 1. 第一版控制范围

第一版支持一个江南大学定义、一份世界存档和至少一个完整世界分支，玩家、苏祈雪、卿为最小闭环，林晚可先进入名册并在适配卡就绪后启用。使用文本私聊和既有 RP 展示，固定版本的卡/地图快照，保留旧单卡模式。

先保存通信事件、阅读观察、必要约定和来源；**不要求第一版就有完整信念图谱、自动日程生成器或通用社会关系推理引擎**。观察原文足以支持多数记忆查询，角色的主观信念可以在后续需要时增补。

世界级分支、权限和失败恢复属于基础，不能留到群聊做完后再补。群聊 UI、精细通知、角色主动串场和大规模存档导入可以晚做。

## 4. 旧存档迁移

推荐默认方案是“保留旧单卡存档＋建立新的世界起点”，而非自动把每张卡的全部聊天合并。不同卡历史可能来自不同日期、不同玩家、不同恋爱阶段，没有可靠统一时间戳和知情标记。

迁移分两种：

### 新世界从开局开始

1. 备份现有 `.rphub` 并验证可读，保持旧存档完整。
2. 导入适配卡，固定原卡快照/哈希、地图版本、玩家和关系绑定。
3. 创建开局事实与每个人的开局观察，区分公开、个人秘密、风格例句。
4. 在新世界命名空间写入初始检查点，先验证两条私聊。

卡牌重构由用户负责；工程提供预检，不自行创造正式卿卡，也不把未解决的室友名单冲突写成定案。

### 希望续接旧剧情

1. 选择一个权威旧角色分支作为时间线锚点，不能按同名自动合并。
2. 原 RP、微信和附件保留为 `legacy_archive`，保存来源 ID、scope 和原时间，默认不把未知视角段落开放给所有 actor。
3. 从可明确识别的消息提取原发送人、收件会话和顺序。混合 NPC 旁白、旧摘要、旧位置推断和未知已读保持未确认。
4. 给出小型“续接快照”供用户校对：当前时间、地点、关系、未决约定、每人明确知道的关键事。不是让用户重写全部历史。
5. 用户确认的快照成为新世界开局种子；不可靠旧摘要仅作档案，不能自行提升为真相或角色记忆。
6. 新分支通过隔离测试后再启用，旧存档仍可打开。

不自动生成原历史中没有证据的阅读事件。不把所有苏卡 RP 旁白都标成苏祈雪亲历。原文存在只能证明被记录过，不能证明内容没受旧幻觉影响。

## 5. 导入导出、删除与回退

世界包应包含：世界定义/规则版本、原卡及编译版本、关系绑定、玩家身份、地图快照、世界分支树与事件、必要投影、未决动作、阅读游标、附件原件和引用清单。索引可重建，但其版本和重建要求必须清楚。

导入前检查 schemaVersion、ID 冲突、分支 parent/forkAtSeq、事件顺序/来源、角色/会话成员、资源引用、快照覆盖、未知动作类型。新旧版本不兼容时明确拒绝或走显式转换，不静默丢未知字段。

恢复通过主库事务提交；若数据很大，先准备并校验数据，再一次切换活跃记录。模型调用和长计算不在事务中进行。配额不足时旧世界仍可恢复打开。

删除角色模板不等于删除世界里已经存在的人物；已固定的卡快照仍需保留。删除某个世界前，资源回收必须考虑其他分支和世界是否引用同一附件。

功能开关建议为独立模式 `legacy_character` / `world_session`，每个存档固定模式。回退时关闭新模式并打开原 legacy 存档；不要尝试把已产生的多人事件无损压回单卡旧 schema。保留世界备份及日志，避免回退丢内容。

## 7. 关键决策与待确认项

已定：世界仅由玩家操作推进；允许 NPC 镜头；读者知识与玩家角色知识分离；苏卡时间线为基准；卿独立于玩家；卡牌由用户后续适配。

本提案的工程默认值：逐角色顺序生成、少量相关人物、按观察过滤、有限传播、世界级历史分叉、纯前端、保留旧模式。这些是可审阅的建议，后续实现可在不破坏认知和因果边界的前提下调整。

真正开始连接正式角色卡时仍需获得：

- 适配后的林晚卡与正式卿卡；最终室友名单。
- 玩家起始人设/姓名与世界具体开局剧情时间。
- 是从新世界开局，还是要续接某个明确旧分支。
- 可接受的单轮延迟/费用，以及是否为不同职责选择不同模型；没有答案时先沿用现有接口并用测试预算验证。

不需要现在决定每个 NPC 的整学期日程、精确回复概率或全部关系权重。由真实场景驱动补充，比先建一套复杂模拟参数更可控。

## 8. 给下一位开发者的接手说明

先读 README 和现状审计，检查当前工作树；不要重置已有修改。然后实现 P0/P1 的窄切面，使用合成夹具，保持用户原卡和旧浏览器数据不变。若需要改 UI，遵守当时有效的仓库组件/设计规则，不凭历史交接中的 UI 描述自行选择组件库。

不调用旧 `tools/refactor/transform.cjs` 重拆应用；它是针对旧单文件的迁移脚本，不是本次多角色重构工具。

交接必须写清：哪些阶段实际实现、哪些仍是提案；新增/修改的存储 schema；旧功能兼容范围；哪些测试真的跑过；真实模型语义尚有哪些失败；如何回到旧模式。

最优先的验收问题始终是：**同一个世界里，卿为何知道取消打球，而苏祈雪为何还相信玩家去打球？能否从每个人的实际请求和事件来源中证明这种差别？**
