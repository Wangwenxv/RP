## 复现与判断

内置浏览器公开站点、苏祈雪「分支 2」、菜单确认 `qwen3.7-plus`。保持剧情时间 2025-03-11 18:30，玩家通过地图设在实验楼 A。真实对话：

1. 玩家「喂喂喂\n怎么不理我」；模型先触发“正在完善角色自身场景”，第二次请求后发送「哪有」「刚回宿舍没看手机」「怎么啦」。地图北苑3栋，314室书桌前。
2. 玩家「刚吃完呀\n在哪吃的\n我刚下课，在实验楼A」；模型回复「在二饭」「你还没吃呀」。这可以是过去用餐地点，不应据此强行移动当前位置。
3. 玩家「没呢\n那我现在去2饭找你？」；观察到位置修正后继续调用工具，计数达到3次模型请求、1次工具调用；最终未发送角色气泡，保留“让对方回复（攒了1条）”。没有取得旧版请求的完整原始响应，不能声称每次失败的精确参数或用户原场景的5次请求都已逐项还原。

代码层确认：微信同时广告 `update_location` 逐字原文核对、`set_position` 自主决定、最终 JSON `position` 三条路径；位置修正请求仍允许查工具；格式示例及收尾提醒没有位置字段，场景协议埋在中间；已知地点回复漏字段也要求付费再生成。旧地理工具曾允许立即修改旧微信正文，在最终 API 失败前落盘。

## 最终契约

- 微信使用独立查询 schema，`tool_geo` 只广告 context/search/place/route/status/batch；最终 `messages` 与 `position` 一起提交自身场景。RP 仍使用已有完整工具。
- 自身场景契约放在 system 最后，提供具体地点 ID 简表；去掉微信旧原文更新指令。过去吃饭地点与当前地点分开，见面邀请不等于任何人已出发。
- 缺失 `position` 时只能保留已确认位置（stay）或有明确目的地的既有行程（continue）；初始未知、显式非法/null位置、明确新出发/到达但漏字段，仍需要一次模型修正。程序不选择新地点、不根据住址自动定位。
- 最终显式 `position` 优先于兼容工具暂存；先剥离推理标记再解析位置。旧 `set_position` 的本轮暂存兼容保留；微信 `update_location` 仅返回 `use_final_position`，不修改旧正文。
- 地图最多两轮查询、最多4次调用；达到预算后移除地图工具。常规微信回合最多4次模型请求（文档/历史检索保留原8轮预算），最后一轮强制结束工具阶段。
- 位置、回复 JSON、图片格式问题合并为一次修正；修正请求撤掉所有工具，直接生成完整 JSON。第二次仍非法明确失败，保留玩家待回复消息；不伪装空回、不保存暂定坐标、不提前调用生图服务。
- 位置跟随接受后的气泡/空回决定存储，原有分支、刷新、玩家控制、行动时间约束继续生效。

位置仍由模型决定，不保证每次自然语言都准确。保留状态不是自动完成行程；缺乏明确新决定时不猜测到达。
