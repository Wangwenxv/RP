审计日期：2026-11-11。范围：磁盘工作树、`docs` 相关交接、用户指定的两张卡。未读取用户浏览器中的实际存档或密钥，未请求真实模型。本次结论不能代表浏览器数据库已经与磁盘角色卡一致。

## 3. 上下文规模

按解析后的字符串长度统计，单位是字符，**不是 token，也不是费用**：

| 卡 | personality | 全部世界书正文 | 常驻世界书正文 | 条目数 |
| --- | ---: | ---: | ---: | ---: |
| 苏祈雪 v2 | 4,086 | 25,593 | 15,477 | 16，其中 10 条常驻 |
| 林晚 | 1,010 | 13,543 | 8,617 | 17，其中 10 条常驻 |

仅两人的 personality＋常驻世界书就有约 29,190 字符，尚未计入历史、玩家、规则、工具和输出。这说明不能把常驻全卡策略直接扩大到整个人物表，但不能据此断言“超过某个长度必然产生幻觉”。实际请求由模式、选中条目、历史与模型接口共同决定，必须记录真实 usage 和请求组成。

历史参考：`docs/request-context-audit.md` 的 42,836 字符请求是旧快照，不是本次实时请求或这两张卡当前相加的结果。

## 4. 地理能力的边界

已有地图与角色分离的方向正确。`geography.js` 的 route 及局部地点检索无需推倒；个人 placeMemories 也适合作为本角色背景。需要改变的是 `project()` 将 user/assistant 映射为两个位置槽的机制，改为明确 actorId 的动作与观察。

地图不是日程表，也没有课表、手机状态、注意力、在线或已读模型。到达、计划、问路已经有区分，应该延续。`wechat-time.js` 的 storyAt 表示虚构时间；新世界钟应收归世界分支。

`app/31-map-library.js:23` 中浏览器保存的同 ID 地图可覆盖内置地图；`:33` 使用 `geographyMaps` 存储。迁移要固定实际使用的地图版本，不能拿磁盘同名 JSON 就认定和旧存档一致。

## 5. 文档与当前工作树不一致

当前分支导出存在明显基线缺口：

- `docs/branch-chat-export.md`、部分架构更新描述 v2 全分支 RP＋微信＋附件导出。
- `index.html:3527` 引用了 `assets/js/branch-chat-utils.js`，但本次磁盘审计该文件不存在。
- `assets/js/data-services.js:929` 的导出版本仍是 `STORY_BRANCH_CHAT_EXPORT_VERSION = 1`。
- 当前 `22-character-io.js` 未接入文档描述的 `RPHubBranchChat/wechatTimeline`；底层也没有文档所述的通用 `setStoredValues` API。

因此该能力应标为“文档已写、工作树未完整落地或文件缺失”，不能当作新世界导出器的成品基础。这不等于整库 `.rphub` 备份不可用，两者是不同路径。本次不顺手修复，实施阶段 0 先核对。

较早文档中“24/27 个模块”“模块加载顺序等于编号”等描述也是历史快照；目前实际加载已到 34，且加载顺序与 setup 调用顺序并非完全按编号。新增模块前应核对 `index.html` 末尾与 `app.js:241` 两处。

## 6. 不能沿用的隐含假设

1. 当前卡就是所有 assistant 发言的作者。
2. 当前角色 scope 中的每段 RP 都是这名角色的经历。
3. 一份世界摘要可以作为所有人物的记忆。
4. 群成员都已读、读到就相信、没有回复就不知道。
5. 地图位置可以直接决定是否看手机。
6. 切换 currentCharacter 可以安全地运行另一个角色子任务。
7. 对旧文本做一次摘要就能恢复可靠的事实与知情人。
8. 假 API 的流程测试能证明真实模型不泄密、不代写。

后续实现应保留现有提示词约束作为补充，但把前七项的关键边界落实到数据和运行时。第八项需要通过分层评测避免过度承诺。
